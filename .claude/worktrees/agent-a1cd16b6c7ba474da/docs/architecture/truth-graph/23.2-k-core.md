**Master:** `23-topology-primitives.md`
**Status:** Design draft (2026-04-29) — under review
**Bead:** to be created post-review

## 1. Purpose

**Question it answers:** How embedded is each entity in the connectivity?

A k-core is the maximal subgraph in which every vertex has degree ≥ k. The **coreness** of a vertex is the largest k for which it is contained in the k-core. This single integer per entity provides a clean, principled answer to "is this entity an orphan, a leaf, or deeply embedded?":

| k_core value | Interpretation |
|---|---|
| 0 | Orphan — entity participates in no active edges |
| 1 | Leaf — entity has at least one neighbour, but is in a tree-like position (removing it doesn't reduce anyone else's connectivity) |
| ≥ 2 | Embedded — entity is part of a more tightly-connected subgraph; removing any one vertex still leaves every other vertex with at least 2 neighbours within the core |

Today the gardener (`ml-services/app/gardener_agent.py`) computes a hand-rolled "sparse leaf" notion in its `get_graph_topology` tool. That logic was a useful first cut but has no formal definition and doesn't compose with other structural concerns. K-core replaces it with a single integer that:

- Has a 50-year-old well-known formal definition (Seidman, 1983)
- Computes in O(n + m) (Batagelj & Zaveršnik, 2003)
- Distinguishes "real but undocumented" entities (low k_core, but in a connected region) from "extraction artefacts" (k=0 orphans with no fixable connections) when paired with embedding-outlier scoring
- Composes cleanly with the rest of `entity_topology` — articulation points, centrality, communities all read the k-core column

K-core is the first primitive that makes the gardener "see" graph structure in a principled way.

## 2. Design

### 2.1 Algorithm

Batagelj & Zaveršnik's O(m) coreness algorithm. Conceptually:

1. Compute the degree of every vertex
2. Repeatedly remove the lowest-degree vertex; assign it a k-core value equal to its degree at removal time
3. Decrement degrees of its neighbours; repeat

The result is a single integer per vertex. Implementation: `igraph.Graph.coreness()` (vendored as part of python-igraph).

The "graph" for k-core is the same undirected projection used by connected components (`23.1` §2.1):
- Active facts (`expired_at IS NULL`)
- Active `same_as_links`
- Self-referential facts excluded
- Direction ignored

### 2.2 Composition with components

A k-core value is meaningful only relative to the entity's component:
- An orphan (k=0) is alone in its own component (component_size = 1)
- A leaf (k=1) is in a component of size ≥ 2 but has only one neighbour
- An embedded entity (k≥2) is in a component of size ≥ 3 with non-trivial structure

The two columns are read together by downstream consumers. The gardener prompt, for example, will say "show me k_core=1 entities in components of size ≥ 5" — narrows to "leaves of large clusters" rather than "any leaf, including in 2-entity clusters."

### 2.3 What k-core does NOT replace

- **Centrality** (`23.5`) — k-core is structural depth, not importance. A leaf entity attached to a major hub has high importance (PageRank) but k=1.
- **Community detection** (`23.4`) — k-core is local density, not modular grouping.
- **Component detection** (`23.1`) — k-core is per-vertex; component is per-subgraph.

K-core is one signal among several. The gardener prompt, post-Phase 2, reads multiple columns together rather than one.

## 3. Implementation

### 3.1 Module location

`ml-services/app/topology.py` (introduced by the `23` master). The k-core-specific function:

```python
def compute_k_core(g: igraph.Graph) -> dict[str, int]:
    """
    Compute coreness for every vertex.

    Returns: dict mapping entity_id (str UUID) to k_core integer.
    """
    coreness_values = g.coreness(mode='all')  # 'all' = treat as undirected
    return {
        g.vs[i]['name']: int(coreness_values[i])
        for i in range(g.vcount())
    }
```

(Pseudocode; `igraph.Graph.coreness()` is the canonical implementation. Returns a list parallel to the vertex order.)

### 3.2 Write-back

Part of the shared `_write_back(results)` per `23` §2.3. The k-core column on `entity_topology`:

```sql
INSERT INTO entity_topology (entity_id, k_core, computed_at, computation_version)
VALUES ($1, $2, NOW(), $3)
ON CONFLICT (entity_id) DO UPDATE SET
  k_core = $2,
  computed_at = NOW(),
  computation_version = $3;
```

Combined with the connected-components write in the unified upsert per `23.1` §3.2.

### 3.3 Gardener integration

The gardener's existing `get_graph_topology` tool computes sparse leaves on the fly. After this ships, the tool reads `entity_topology.k_core` directly. Two changes:

1. **Tool implementation update:** `get_graph_topology` queries `entity_topology` for `k_core <= 1` entities, ranked by `component_size DESC` (so leaves of larger structures surface first). Removes the hand-rolled traversal logic.
2. **Gardener prompt update:** the prompt's existing "sparse leaves" framing is replaced with "low k-core entities". The prompt continues to prioritise sparse entities for cross-linking but the language is now grounded in the formal definition.

These changes ship in the bead implementation; design doc only mentions the contract.

### 3.4 No new endpoint

K-core is read through:
- `GET /api/entities/:id` (extended in `23.1` §3.3 to include all topology columns)
- The gardener's `get_graph_topology` MCP tool, which now reads the column

No standalone endpoint is needed.

## 4. Verification

### 4.1 Manual checks

- After `topology/compute` on an empty graph: no rows; no error
- After compute on a graph with a known star topology (1 hub, N leaves): hub has k_core=1, all leaves have k_core=1 (every vertex has degree 1 in a star)
- After compute on a complete graph K₄ (4 entities pairwise connected): every vertex has k_core=3
- After expiring a fact that causes an entity to become an orphan: next compute reports k_core=0 for that entity

### 4.2 Automated tests

Test file `platform/src/test/harness/topology-kcore.test.ts`.

- **Empty graph:** no rows.
- **Single entity:** one row, k_core=0.
- **Two entities with no edge between them:** both k_core=0.
- **Two entities with one fact between them:** both k_core=1.
- **Star (1 hub + 4 leaves):** hub k_core=1, every leaf k_core=1. (In a star: leaves have degree 1; coreness peeling removes them at k=1; the hub is left isolated and gets k_core=1 too. Cold-eyes review B4 — the original justification incorrectly claimed all vertices have degree 1, but the hub has degree 4.)
- **Triangle (3 entities, pairwise connected):** all three have k_core=2.
- **Complete K₄:** all four have k_core=3.
- **Path graph (A-B-C-D):** all have k_core=1 (every vertex has degree ≤ 2 but coreness depends on iterative pruning; in this case every vertex peels at degree 1).
- **Star plus extra edge between two leaves:** two of the leaves have k_core=2, one has k_core=1, hub has k_core=2.
- **Self-referential fact ignored:** entity with one self-fact and no other connections has k_core=0.
- **Expired fact excluded:** create A-B fact, expire it, recompute. Both A and B have k_core=0 (assuming no other edges).
- **same_as link counted:** create entities A, B with no facts; create same_as link; both have k_core=1.
- **Determinism:** run compute twice; assert k_core values identical for every entity.
- **Snapshot benchmark:** load `synthetic-10k`, compute, assert `k_core` distribution matches generator parameters within ±5% (the generator's `facts_per_entity_mean` controls expected k-core distribution).

### 4.3 Acceptance criteria for `bd close`

- All §4.2 tests pass on a clean `pnpm test` and `pnpm test:snapshot` run
- Manual checks (§4.1) pass
- Benchmark report committed (§5.2)
- Cross-feature integration: k_core values surface correctly when full `topology/compute` runs (no conflict with connected-components or articulation that share the same write)
- Gardener integration ships separately; the prompt change uses k_core ≤ 1 instead of hand-rolled sparse-leaf logic, and `get_graph_topology` reads the column (verified via integration test on the gardener side)
- No regression in audit-trail, edge-lifecycle, source-refs, blast-radius, contradictions, or pattern test suites

## 5. Benchmark

### 5.1 Acceptance thresholds

K-core via igraph is O(n + m), comparable to connected components.

| Graph size | Target | Hard cap |
|---|---|---|
| 100 entities | < 5 ms | 30 ms |
| 1 000 entities | < 30 ms | 100 ms |
| 10 000 entities | < 200 ms | 800 ms |

These cover `compute_k_core(g)` in isolation.

### 5.2 Baseline reports

Committed under `platform/src/test/data/phase2-topology/benchmark-reports/k-core/`:

- `synthetic-1k-kcore.json`
- `synthetic-10k-kcore.json`
- `frankenstein-10chunks-kcore.json`
- `mixed-narrative-technical-1k-kcore.json`

Each JSON: `{snapshot_name, total_entities, k_core_distribution: {0: N0, 1: N1, 2: N2, ...}, max_k_core, mean_k_core, elapsed_ms}`.

### 5.3 What we measure over time

- **k-core distribution shape** — most graphs follow a power-law-like decline. A sudden shift in the distribution between regenerations suggests extraction or reconciliation behaviour change.
- **max_k_core** — the deepest k-core value. Should grow logarithmically with edge density. Sudden jumps signal a corpus introducing dense subgraphs (e.g. a new technical document with heavy cross-referencing).
- **Latency growth** — should be near-linear in m (edges). Quadratic growth signals an algorithm regression.
- **Orphan rate one-way containment** (cold-eyes review W3) — `entity_topology.k_core = 0` set should be a *subset* of `graph_stats.orphan_rate` set, not equal. They differ on graph projection: k-core counts same_as links as edges, but `graph_stats.orphan_rate` per `22` §3.2 counts active facts only. An entity with no facts but a same_as link has `k_core = 1` (not orphan by k-core) but is an orphan by `orphan_rate`. The check is "every k_core=0 entity is also in the orphan set"; reverse containment doesn't hold.

## 6. Edge cases

| Case | Expected behaviour |
|---|---|
| Empty graph | No rows. |
| Single entity (no edges at all) | k_core = 0. |
| Two entities, no edge | Both k_core = 0. |
| Two entities, one fact | Both k_core = 1. |
| Star graph (1 hub, N leaves) | Every vertex k_core = 1. |
| Triangle | All three k_core = 2. |
| Path graph (A-B-C-D) | All four k_core = 1. |
| Complete K_n | Every vertex k_core = n-1. |
| Self-referential facts | Excluded; do not contribute to coreness. |
| Expired facts | Excluded; entity may become an orphan. |
| Active same_as link | Counts as an edge for coreness. |
| Cascade-delete (entity removed) | ON DELETE CASCADE removes the row; next compute resyncs neighbouring k-core values (a deleted neighbour reduces remaining vertices' degrees, which may lower their k_core). |
| Disconnected components | k-core computed per-component implicitly — coreness is a local property; an isolated triangle and an isolated edge produce k_core values 2 and 1 respectively, regardless of being in different components. |
| Very high-degree hub in a sparse graph | The hub's k_core is bounded by the coreness of its neighbours, not its own degree. A 100-leaf star still has hub k_core = 1. |

### 7.2 Evolution signals

The `test-harden` Test-Data Evolver subagent watches for:

- **k_core distribution shifts on the same corpus across regenerations** — either reconciliation behaviour changed, or the test fixture set needs to lock against the new shape
- **A real corpus produces a wider k-core range than any fixture covers** — extend fixtures to capture the deepest core
- **Gardener integration regression** — the post-shipped gardener prompt picks different sparse-leaf candidates than expected; fixture extension to localise

### 7.3 "Done enough"

K-core is "done enough" when:

- All §4.2 tests pass
- Benchmark report committed for all four baseline snapshots
- Gardener integration test passes — `get_graph_topology` returns expected ranking on a fixture
- Orphan-rate one-way containment check passes (k_core=0 set ⊆ `graph_stats.orphan_rate` entities). Equality NOT required — same_as-only entities legitimately differ.
- No regressions in upstream test suites

### 7.4 Forward evolution

- **Combination signals**: k_core ≤ 1 + embedding outlier (HDBSCAN noise label, Phase 3) is a strong "extraction artefact" signal worth surfacing to the gardener as a high-priority cleanup target. Phase 3 design doc captures this combination.
- **Per-component k_core distribution**: future viz could plot per-component k_core histograms. No code commitment, just noting the data is now available.
- **k-truss (ξ-truss)**: a stronger primitive than k-core for finding dense subgraphs. Out of scope for Phase 2; could land as a Phase 3+ extension if needed.
