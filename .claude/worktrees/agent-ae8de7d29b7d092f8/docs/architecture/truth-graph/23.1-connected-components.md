## 1. Purpose

**Question it answers:** What islands exist in the graph?

A connected component is a maximal subset of entities where every entity in the subset is reachable from every other via the active fact graph (plus `same_as` links, which connect entities semantically). Two entities in different components share no relational path.

Today the system is blind to this. Cross-component pairs are the explicit gap behind `nmemo-a7f` — they're the candidates for cluster bridging. Without `component_id` per entity, the question "are these two entities in the same island, or different ones?" cannot be phrased in SQL. After this ships, the cross-cluster generator (Phase 4) walks `(component A, component B)` pairs above a size threshold and feeds candidates to the existing `reconciliation_agent`.

This is also the foundation for several Phase 1 / 2 / 3 reads:
- `graph_stats.embedding_cluster_count` (Phase 1, populated by Phase 3) is conceptually distinct but operationally similar — components are graph-edge islands; embedding clusters are semantic-space islands; both are "natural groupings"
- Articulation point computation (`23.3`) requires knowing which component an articulation belongs to
- Centrality (`23.5`) is computed per-component for some metrics (PageRank works graph-wide; betweenness is sometimes restricted)

## 2. Design

### 2.1 Component definition

The "graph" for component detection is built from:
- All entities that exist (`SELECT id FROM entities`)
- All **active** fact edges (`facts WHERE expired_at IS NULL`) — directionality ignored, treated as undirected
- All **active** same_as links (`same_as_links` — every row is currently active; no expiry on this table)

Self-referential edges (subject = object on attribute facts) are excluded from component detection — they don't change connectivity.

Expired facts and merged-out entities (cascaded delete) are excluded by the export query.

### 2.2 Algorithm

Standard breadth-first traversal over the undirected projection. NetworkX `connected_components(G)` or igraph `connected_components(mode='weak')` — both O(n + m).

The export and traversal are part of the unified `topology/compute` routine in `23` §2.3; `compute_components(g)` is one of five `compute_*` functions sharing the in-memory graph.

### 2.3 Component ID assignment

Components returned by NetworkX/igraph are unordered sets. We assign deterministic integer IDs by:

1. Sorting components by **size descending** (largest first)
2. Within equal-size components, sorting by the lexicographically smallest UUID of any member (deterministic given the entity set)
3. Assigning IDs `0, 1, 2, …` in that order

This determinism matters: re-running compute on the same graph state produces the same `component_id` values, so downstream consumers (including the reasoning agent's prompts and viz colour assignments) don't see spurious churn.

### 2.4 Size and persistence

Each entity's row in `entity_topology` carries:
- `component_id` — the integer ID per §2.3
- `component_size` — total entity count of this entity's component

`component_size` is denormalised — it's redundant with `COUNT(*) WHERE component_id = X` but cheap to write and removes a JOIN from the hot path. Phase 4's cross-cluster generator iterates large-component pairs by reading both fields directly.

### 2.5 Same_as link semantics

A `same_as` link between two entities is an explicit identity statement: they refer to the same real-world referent. For component detection this is treated as an edge that connects them — after the link exists, they share a component. This means: when reconciliation creates a `same_as` link bridging two previously-disconnected clusters, the next `topology/compute` will report a single merged component covering both.

Direction: `same_as_links.entity_a_id < entity_b_id` per the schema; for component detection both sides are interchangeable.

## 3. Implementation

### 3.1 Module location

`ml-services/app/topology.py` (introduced by the `23` master). The connected-components-specific function:

```python
def compute_components(g: igraph.Graph) -> dict[str, tuple[int, int]]:
    """
    Compute connected components on the undirected graph.

    Returns: dict mapping entity_id (str UUID) to (component_id, component_size).
    """
    # igraph returns a VertexClustering; iterate to get vertex-index lists per component
    raw_components = g.connected_components()  # mode kw redundant on undirected; omit
    component_lists = [list(component) for component in raw_components]

    # Canonical sort: size desc, then smallest member UUID asc
    sorted_components = sorted(
        component_lists,
        key=lambda members: (-len(members), min(g.vs[i]['name'] for i in members))
    )

    # Assign IDs 0..N-1 in canonical order
    result: dict[str, tuple[int, int]] = {}
    for component_id, members in enumerate(sorted_components):
        size = len(members)
        for vertex_idx in members:
            entity_id = g.vs[vertex_idx]['name']
            result[entity_id] = (component_id, size)
    return result
```

### 3.2 Write-back

Part of the shared `_write_back(results)` in `topology.py`. For each entity:

```sql
INSERT INTO entity_topology (entity_id, component_id, component_size, computed_at, computation_version)
VALUES ($1, $2, $3, NOW(), $4)
ON CONFLICT (entity_id) DO UPDATE SET
  component_id = $2,
  component_size = $3,
  computed_at = NOW(),
  computation_version = $4;
```

Other features' columns (`k_core`, `pagerank`, etc.) are written by the same upsert in the unified pass — see `23` §2.3.

### 3.3 No new endpoint

Component computation is invoked through the shared `POST /api/topology/compute`. There is no `POST /api/topology/components` — splitting per-feature endpoints would duplicate the graph export cost.

For querying after compute, two read patterns are surfaced via existing endpoints:

- `GET /api/entities/:id` returns `entity_topology` columns inline (a small extension to the existing entity-detail endpoint)
- `GET /api/components/:component_id` (new, lightweight) returns the entity list for a given component, ordered by name

The component-list endpoint is for viz / debug; not load-bearing.

## 4. Verification

### 4.1 Manual checks

- After `topology/compute` on an empty graph: no rows in `entity_topology`
- After compute on a single-entity graph: one row, `component_id=0`, `component_size=1`
- After ingesting two disconnected source documents: two components, each containing the entities from one document
- After reconciliation creates a `same_as` link bridging two clusters: next compute reports one component spanning both

### 4.2 Automated tests

Test file `platform/src/test/harness/topology-components.test.ts` (uses fixture-based testing per `18-test-data-hardening-protocol.md`).

- **Empty graph:** compute returns no rows. `SELECT COUNT(*) FROM entity_topology = 0`.
- **Single entity:** one row; `component_id=0`, `component_size=1`.
- **Two disconnected entities (no facts):** two components, each size 1, IDs 0 and 1, deterministic ordering by UUID.
- **Star graph (hub + 3 leaves):** one component, size 4, all four entities share `component_id=0`.
- **Two clusters of different sizes (5 vs 3):** two components, larger gets `component_id=0`, smaller gets `component_id=1`. Sizes 5 and 3 respectively.
- **Same_as link bridges two clusters:** before — two components; create same_as link; recompute — one component covering both.
- **Expired facts excluded:** create entity A and B with one fact between them, expire the fact, recompute. They're now in different components (the only edge is gone).
- **Self-referential fact ignored:** entity with a self-fact has component_size = 1 (not 2). The self-edge contributes nothing to connectivity.
- **Determinism:** run compute twice on the same graph state; assert all `component_id` values identical.
- **Idempotency on recompute with no graph change:** rows updated (`computed_at` advances), but `component_id` and `component_size` unchanged.
- **Snapshot benchmark:** load `synthetic-10k`, compute, assert every entity has a non-NULL `component_id` and the component count matches the snapshot's expected (per `cluster_count` generator param).

Test names follow the existing pattern (see `phase4-blastradius` and `phase6-patterns` test files).

### 4.3 Acceptance criteria for `bd close`

- All §4.2 tests pass on a clean `pnpm test` and `pnpm test:snapshot` run (the snapshot suite is the dedicated serial config per `28` §3.6)
- Manual checks (§4.1) pass
- Benchmark report committed (§5.2)
- Cross-feature integration: component IDs surface correctly when the full `topology/compute` runs (i.e. doesn't conflict with k-core or articulation that share the same write-back)
- No regression in audit-trail, edge-lifecycle, source-refs, blast-radius, contradictions, or pattern test suites

## 5. Benchmark

### 5.1 Acceptance thresholds

| Graph size | Target | Hard cap |
|---|---|---|
| 100 entities, ~300 edges | < 10 ms | 50 ms |
| 1 000 entities, ~3k edges | < 50 ms | 200 ms |
| 10 000 entities, ~30k edges | < 300 ms | 1 000 ms |

These cover the "compute_components(g)" function in isolation, not including the shared graph export and write-back (those are amortised across all five features per `23` §5.1).

### 5.2 Baseline reports

Committed under `platform/src/test/data/phase2-topology/benchmark-reports/components/`:

- `synthetic-1k-components.json`
- `synthetic-10k-components.json`
- `frankenstein-10chunks-components.json` (correctness — components should match expected narrative grouping)
- `mixed-narrative-technical-1k-components.json` (correctness — multi-source corpus produces multiple components)

Each JSON: `{snapshot_name, total_entities, component_count, largest_component_size, smallest_component_size, mean_component_size, elapsed_ms_compute_only}`.

### 5.3 What we measure over time

- **Latency growth** as a function of (n, m). Linear is expected for BFS.
- **Component-count drift** when re-ingesting the same corpus. Drift indicates extraction/reconciliation behaviour change, not a component-detection bug.
- **Correctness on snapshot ground-truth**: the synthetic generator parameterises `cluster_count`; the resulting `component_count` should equal `cluster_count` minus any cluster pairs the generator linked via the optional `same_as` step (per `28` §3.3 step 11).

## 6. Edge cases

| Case | Expected behaviour |
|---|---|
| Empty graph | No rows written; `entity_topology` empty for components. No error. |
| Single entity | One row; `component_id=0`, `component_size=1`. |
| Two disconnected entities | Two components. ID assignment deterministic by UUID. |
| Star graph (one hub, N leaves) | One component, size N+1. |
| Cycle (A→B, B→C, C→A) | One component, size 3. (Direction ignored; cycle is just a connected subgraph.) |
| Self-referential fact (subject=object) | Excluded from component detection. The entity's component reflects only its other neighbours. |
| Expired fact between two entities | Edge ignored. If it was their only connection, they're now in separate components. |
| Active `same_as` link between two entities | Counts as an edge. They share a component after the link is created. |
| Cascade-delete (entity removed by `merge_entities()`) | The entity's `entity_topology` row is removed by ON DELETE CASCADE. Next compute cycle resyncs component assignments for remaining entities. |
| Concurrent compute in flight | Per `23` §8.1, second call short-circuits via the `topology_compute_runs` in_progress check. |
| Compute called mid-ingest (rows being inserted) | Component assignment reflects the export-time snapshot. New entities appear after the next compute cycle. |
| Equal-size components (e.g. two pairs of disconnected entities) | Ordered by smallest-member-UUID for determinism. Test asserts deterministic ordering. |
| Very large single component (>50% of entities) | No special behaviour. Component_size reflects reality. Phase 4's cross-cluster generator can apply size thresholds when iterating pairs. |

## 7. Iteration cycle

### 7.1 Initial fixtures (this ship)

Under `platform/src/test/data/phase2-topology/components/`:

```
fixtures/
├── empty-graph.sql              -- no entities, no facts
├── single-entity.sql            -- 1 entity
├── two-disconnected.sql         -- 2 entities, no facts
├── star.sql                     -- 1 hub + 3 leaves with facts radiating
├── two-clusters-5-3.sql         -- 5+3 entities in two disconnected clusters
├── bridged-via-sameas.sql       -- 2 clusters connected by a same_as link
├── expired-fact-bridge.sql      -- 2 clusters, the only bridge is an expired fact
└── cycle.sql                    -- 3 entities forming a cycle

expected/
├── empty-graph.expected.json
├── single-entity.expected.json
└── ...
```

Each `expected.json` follows the `simple-mutations.expected.json` schema (see Phase 1 audit-trail tests).

### 7.2 Evolution signals

The `test-harden` Test-Data Evolver subagent watches for:

- **Real-world ingest produces unexpected component count** — propose a fixture covering that topology
- **Component drift across regenerations of the same LLM snapshot** — investigate whether reconciliation behaviour changed; may extend fixtures to lock the drift
- **Phase 4 cross-cluster generator finds the same bridge candidate set repeatedly without progress** — fixture to test "what happens when components are nearly-connected but never bridged"
- **Snapshot benchmark regression** — fixture extension to localise the cause

### 7.3 "Done enough"

Connected-components is "done enough" when:

- All §4.2 tests pass
- Benchmark report committed for all four baseline snapshots
- One real-world ingest (any non-trivial corpus) produces a sensible component count and the largest component covers a recognisable narrative or topical subset
- No regressions in upstream test suites

The bead's acceptance criteria mirror this list.

### 7.4 Forward evolution

Phase 4's cross-cluster generator (`25-cross-cluster-generator.md`) is the primary downstream consumer. When Phase 4 ships:

- Fixtures gain explicit "expected cross-component candidate pairs" annotations
- The benchmark suite extends to measure how component IDs feed into the candidate-generation pipeline

Phase 3's drift detection (`24.2`) is independent — it operates per-entity in semantic space, not on graph topology. No coupling.
