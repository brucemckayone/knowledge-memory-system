## 1. Purpose

**Question it answers:** Which entities or edges, if removed, would split the graph?

An **articulation point** (also called cut vertex) is a vertex whose removal increases the number of connected components. A **bridge** is an edge whose removal does the same. Together they identify the structurally critical pieces of the graph — the load-bearing entities and edges whose loss has the largest blast radius.

Two operational uses:

1. **Safety flag for destructive operations.** Before `merge_entities()` deletes a source entity, before `expireFact()` invalidates a fact, before the gardener decides "this orphan can go" — knowing whether the target is an articulation point or bridge tells us whether the operation will fragment the graph. Deletion of an articulation point splits at least one component into two; expiring a bridge fact does the same for an edge.

2. **High-priority reconciliation candidates.** After Phase 4's cross-cluster generator creates a `same_as` link between previously-disconnected clusters, that link's edge becomes (almost by definition) a bridge. Identifying it confirms the structural payoff of the bridging decision and provides a tight integration test for the cross-cluster generator.

This pairs naturally with k-core (`23.2`): an entity that is both a leaf (k_core=1) AND an articulation point is structurally dangerous — losing it disconnects something. Combined signals like "k_core ≤ 1 AND is_articulation_point" surface high-stakes entities for special handling.

## 2. Design

### 2.1 Algorithm

Tarjan's depth-first articulation algorithm, O(n + m). Implementation: `igraph.Graph.articulation_points()` and `igraph.Graph.bridges()`. Both are O(n + m) in igraph; same shared graph projection as components and k-core.

**Articulation points:** computed first, output as a list of vertex indices. Mapped back to entity IDs.

**Bridges:** computed independently (Tarjan's algorithm has a closely-related variant for edges). Output is a list of edge indices, mapped back to either:
- A `fact_id` (if the bridge is a fact edge in the active graph)
- A `same_as_link_id` (if the bridge is a same_as link)

### 2.2 What is and isn't a "bridge edge"

The `topology_bridges` table (defined in master `23` §2.2) accommodates exactly two edge types — fact edges and same_as links. We do not track bridges over edges that don't have a stable ID (e.g. the projection's undirected representation collapses multi-edges; we keep one `fact_id` per direction).

**Multi-edge handling:** a fact A→B and a same_as A↔B both connect A and B. When projected to undirected, they're parallel edges. Bridge analysis treats them as one edge (any edge connecting A and B is sufficient to maintain connectivity). The `topology_bridges` row records whichever edge representative igraph returned; this is deterministic given a consistent edge-ordering during graph export.

### 2.3 Scope of the bridge table

`topology_bridges` is rewritten on every successful compute. Old bridges are deleted; new bridges inserted. There is no history per cold-eyes review B3 / `23` §2.6 — the table reflects the most recent compute.

If a downstream consumer needs to track "edge X used to be a bridge but isn't now," that's drift over time, captured by the analogous Phase 3 mechanism for entities. We don't extend bridges to a history layer in Phase 2.

### 2.4 Per-component vs global

Articulation points are inherently per-component — an articulation in component A is irrelevant to component B. Tarjan's algorithm runs per-component implicitly (a DFS forest visits one component at a time). The output is a flat list spanning all components.

A vertex in a component of size 1 (orphan) cannot be an articulation point — there's nothing to split. A vertex in a component of size 2 (a pair connected by one edge) is also not an articulation point — removing it leaves a single vertex, which is one component (still). The smallest non-trivial articulation candidates are in components of size ≥ 3.

## 3. Implementation

### 3.1 Module location

`ml-services/app/topology.py`. Two functions:

```python
def compute_articulation(g: igraph.Graph) -> set[str]:
    """Returns the set of entity_ids that are articulation points."""
    indices = g.articulation_points()
    return {g.vs[i]['name'] for i in indices}

def compute_bridges(g: igraph.Graph) -> list[BridgeRecord]:
    """Returns a list of BridgeRecord(source_id, target_id, fact_id|same_as_id)."""
    indices = g.bridges()
    return [
        _resolve_bridge(g, edge_idx) for edge_idx in indices
    ]
```

`_resolve_bridge` looks up the edge's source/target entity IDs and the originating `fact_id` or `same_as_link_id` from the export-time edge metadata.

### 3.2 Write-back

Articulation points contribute to the **canonical unified upsert** in master `23` §2.3.2 — `is_articulation_point` is one column among many in the bulk upsert. This doc does NOT define a per-feature UPDATE.

For bridges (`topology_bridges`), the rewrite happens via the canonical pattern in master `23` §2.3.2:

```sql
-- Step 1: unconditional delete (cold-eyes review B1 — drop computation_version filter)
DELETE FROM public.topology_bridges;

-- Step 2: bulk insert with canonical ordering enforced per row
-- The CHECK constraint topology_bridges_ordering requires source_entity_id < target_entity_id;
-- igraph.bridges() returns edges in DFS-discovery order, which does NOT respect this.
-- Each row construction MUST use LEAST/GREATEST before insert.
INSERT INTO public.topology_bridges
  (source_entity_id, target_entity_id, fact_id, same_as_link_id, computation_version)
VALUES
  (LEAST($1::uuid, $2::uuid), GREATEST($1::uuid, $2::uuid), $3, $4, $5),
  ...
ON CONFLICT (source_entity_id, target_entity_id) DO NOTHING;
```

The Python-side helper:

```python
def _build_bridge_row(g, edge_idx, computation_version):
    edge = g.es[edge_idx]
    src_uuid = g.vs[edge.source]['name']
    dst_uuid = g.vs[edge.target]['name']
    a, b = (src_uuid, dst_uuid) if src_uuid < dst_uuid else (dst_uuid, src_uuid)
    edge_kind = edge['kind']  # populated by _export_graph per master 23 §2.3.1
    fact_id = edge['edge_id'] if edge_kind == 'fact' else None
    same_as_link_id = edge['edge_id'] if edge_kind == 'same_as' else None
    return (a, b, fact_id, same_as_link_id, computation_version)
```

Both within the same transaction as the rest of the unified compute. (Cold-eyes review B1 fix: canonical ordering enforced; DELETE unconditional.)

### 3.2.1 Partial-failure semantics (cold-eyes review W9)

If any feature within the unified compute raises (articulation or bridge specifically — or any sibling), the entire transaction rolls back. `entity_topology` retains the previous compute's values; `topology_compute_runs.status='failed'` with `error_detail` recording which feature raised. No half-update state is possible — see master `23` §2.3.3.

### 3.3 Read patterns

Articulation:
- `SELECT entity_id FROM entity_topology WHERE is_articulation_point = TRUE` — uses the partial index defined in `23` §2.1
- Common filter: `is_articulation_point = TRUE AND component_size ≥ N` — narrows to articulations in non-trivial components

Bridges:
- `SELECT * FROM topology_bridges` — small table; full-scan acceptable
- Filter by `fact_id` to ask "is this fact a bridge?" before expiring it
- Filter by `same_as_link_id` to ask "is this same_as link the only thing holding two clusters together?"

### 3.4 Integration with destructive operations

Two integration points in the platform code (shipped as part of this bead, not separately):

1. **`expireFact(factId, reason)`** in `src/services/facts.ts` — before expiring, check `topology_bridges WHERE fact_id = $1`. If a row exists, log a warning that includes the source/target entities and the resulting cluster fragmentation. Do not block — the operation may be intentional. The warning surfaces in the gardener and reasoning-agent reports.

2. **`merge_entities()` SQL function** in `005_reconciliation.sql` — out of scope to modify the function. Instead, the agent tool wrappers (`execute_merge` in `causal-agent.ts`) check `entity_topology.is_articulation_point` for both source and target before invoking the function. If either is an articulation point, log a structural-impact warning.

Neither integration blocks the operation; both surface the structural cost.

## 4. Verification

### 4.1 Manual checks

- After `topology/compute` on a single-entity graph: no articulation points, no bridges
- After compute on a graph with a known bridge (two clusters connected by a single fact): one bridge in `topology_bridges`, both endpoints flagged as articulation points
- After Phase 4's cross-cluster generator creates a `same_as` link bridging two clusters and topology recomputes: that same_as link appears in `topology_bridges` (the integration test for `nmemo-a7f`'s primary milestone)

### 4.2 Automated tests

Test file `platform/src/test/harness/topology-articulation.test.ts`.

- **Empty graph:** no articulation points, no bridges.
- **Single entity:** no articulation, no bridges.
- **Two entities, one fact:** that fact is a bridge; both endpoints are not articulation points (removing either leaves one entity, which is one component, no split).
- **Path graph A-B-C-D:** every internal vertex (B, C) is an articulation point; A and D are not. Every edge is a bridge.
- **Triangle (3 entities, pairwise connected):** no articulation points, no bridges (every vertex has 2 disjoint paths to every other).
- **Two triangles connected by one edge:** the connecting edge is a bridge; its two endpoints are articulation points.
- **Star (1 hub, 4 leaves):** the hub is an articulation point; every spoke is a bridge.
- **same_as link bridges two otherwise-disconnected clusters:** the link appears in `topology_bridges` with `same_as_link_id` populated.
- **Bridge vs non-bridge across multi-edges:** if A-B has a fact AND a same_as link, removing one still leaves connectivity; neither is a bridge. (Tests multi-edge handling.)
- **Articulation point in a component of size 2:** none — a pair connected by an edge has no articulation.
- **Cascade-delete impact:** delete an articulation entity (via merge); next compute recalculates; the formerly-articulated component now reflects the post-merge state.
- **Determinism:** same graph state produces same articulation set + bridge set across recomputes.
- **Snapshot benchmark:** `synthetic-10k` — articulation count and bridge count match generator-derived expectations within tolerance.

## 5. Benchmark

### 5.1 Acceptance thresholds

Tarjan articulation/bridge detection is O(n + m).

| Graph size | Target | Hard cap |
|---|---|---|
| 100 entities | < 5 ms | 30 ms |
| 1 000 entities | < 30 ms | 100 ms |
| 10 000 entities | < 250 ms | 1 000 ms |

Articulation and bridge computations are run separately; targets cover both summed.

### 5.2 Baseline reports

Under `platform/src/test/data/phase2-topology/benchmark-reports/articulation/`:

- `synthetic-1k-articulation.json`
- `synthetic-10k-articulation.json`
- `frankenstein-10chunks-articulation.json`
- `mixed-narrative-technical-1k-articulation.json`

Each: `{snapshot_name, articulation_point_count, bridge_count, articulation_rate (= count/total_entities), elapsed_ms_articulation, elapsed_ms_bridges}`.

### 5.3 What we measure over time

- **Articulation rate** is corpus-dependent. Tree-shaped graphs have high rates; densely-connected ones have low rates. A sudden change between regenerations signals a structural shift.
- **Bridge count** vs same_as link count after Phase 4. If most same_as links are bridges, Phase 4 is doing real cluster bridging. If few are, candidates are bridging trivial pairs.
- **Latency growth** linear in m. Quadratic signals an algorithm regression.

## 6. Edge cases

| Case | Expected behaviour |
|---|---|
| Empty graph | No rows. |
| Single entity | Not articulation; no bridges. |
| Two entities, one fact | Edge is a bridge; neither endpoint is an articulation point. |
| Two entities, two parallel edges (fact + same_as) | Neither edge is a bridge. |
| Triangle | No articulations, no bridges. |
| Tree (path, star, deep tree) | Every internal vertex is articulation; every edge is bridge. |
| Cycle | No articulations, no bridges. |
| Cycle plus a pendant (cycle + one extra leaf attached) | The cycle vertex with the pendant is articulation; the pendant edge is a bridge. |
| Component of size 1 | Vertex is not articulation. |
| Component of size 2 | No articulation. |
| Multi-edges (fact + same_as on same pair) | Treated as connected via either; bridge analysis sees a single representative edge. |
| Self-referential fact | Excluded from graph projection; doesn't affect articulation. |
| Concurrent compute | Per `23` §8.1, second call short-circuits. |
| Bridge over an expired fact | The fact is excluded from projection; edge doesn't appear. |
