## 1. Purpose

**Question it answers:** What natural groupings does the graph reveal?

A community is a maximally-cohesive subgraph — entities more tightly connected to each other than to the rest of the graph. Connected components answer "what islands exist?"; communities answer "within an island, what natural sub-groupings exist?". Two entities can be in the same component (reachable via a path) but in different communities (the path goes through several intermediaries; their direct connectivity is sparse).

Communities provide the system with **automatically-discovered groupings** without labels:
- For Phase 4's cross-cluster generator, "different communities within the same component" is a signal — entities playing different roles in the same narrative are not the same identity, but cross-community pairs in *different* components are stronger candidates than random cross-component pairs
- Doc 06 line 207's example query "show me all entities from cluster X" is unblocked
- The reasoning agent's prompts can include "you are looking at the medical-research community within this corpus" framing
- Community boundaries are interesting per se — entities at boundaries (high `participation_coef`) sit between groupings and may be content bridges or domain integrators

This is the first capability that gives the system access to *unsupervised structure*. Components and k-core are mechanical — communities are discovered.

## 2. Design

### 2.1 Algorithm: Leiden, not Louvain

Leiden (Traag, Waltman & van Eck, *Sci Rep* 2019) is the descendant of Louvain that fixes Louvain's "badly-connected community" bug — Louvain can return communities that are internally disconnected, which is nonsensical. Leiden guarantees connected, well-defined communities at every level.

Implementation: `leidenalg` Python package, which sits on top of `python-igraph`. Both ship as part of the Phase 2 dependency add per master `23` §2.5.

**Algorithm at a glance:** local moves of vertices between communities to maximise modularity, with a refinement step that can split badly-connected sub-communities. O(m log n) typical; sublinear in the number of communities.

### 2.2 Modularity vs alternatives

We use modularity-maximisation (Leiden's default objective) rather than:
- **Infomap** (random-walk based) — better for flow-driven graphs but heavier dependency, slower
- **Spectral clustering** — eigendecomposition is O(n³) dense; impractical above 1k entities
- **Stochastic block models** — principled but require pickier parameter tuning

Modularity has well-known limitations (resolution limit — small communities get absorbed in dense graphs; Fortunato & Barthélemy, PNAS 2007). At our scale (1k–10k entities) the resolution limit is unlikely to bite, but we acknowledge the limitation in §6.

### 2.3 Resolution parameter

Leiden's resolution parameter γ controls community size: higher γ means more, smaller communities; lower γ means fewer, larger communities. Default 1.0 (the standard modularity formulation).

**We commit to γ = 1.0 initially.** Tuning is deferred to the iteration cycle — if real corpora produce communities that are too coarse-grained or too fine-grained, the benchmark reports surface this and we tune. Resolution sweeps are recorded in `topology_compute_runs` so we can audit changes.

### 2.4 Determinism

Leiden has a randomised initial assignment. **`leidenalg.find_partition()` does NOT accept a `seed=` kwarg in 0.10.x** (cold-eyes review W2). Determinism is set at the igraph level instead:

```python
import random
import igraph
import leidenalg

seed_val = compute_seed(computation_version)  # deterministic from version + salt
rng = random.Random(seed_val)
igraph.set_random_number_generator(rng)
partition = leidenalg.find_partition(g, leidenalg.ModularityVertexPartition, n_iterations=2)
```

Identical `computation_version` + identical input + identical seed-derivation salt → identical community assignments.

This matters: re-running compute on the same graph state must produce the same `community_id` values. Otherwise downstream colour assignments, prompt phrasings, and any consumer caching all churn unnecessarily.

### 2.5 Per-component or whole-graph

Leiden runs whole-graph; communities respect component boundaries automatically (a community is a connected subset, so it cannot span disconnected components). For each component, Leiden produces zero or more communities depending on internal structure. A trivial component (size 1 or 2) becomes its own community. Larger components fragment into multiple communities iff modularity-maximising warrants it.

`community_id` is globally unique across all components, mirroring `component_id` assignment from `23.1`. ID assignment uses the same determinism rules: sort communities by size descending, with smallest-member-UUID tiebreak.

### 2.6 Participation coefficient

The Guimerà-Amaral participation coefficient (Nature 2005) measures how much an entity's edges spread across communities:

```
P(v) = 1 - sum_over_communities_c [ (k_v_c / k_v)² ]
```

Where `k_v` is `v`'s degree and `k_v_c` is the number of `v`'s edges going to community `c`. P=0 means all `v`'s edges are within its own community ("provincial"); P close to 1 means edges spread across many communities ("connector").

Cheap to compute given community assignments — single pass per vertex. Stored in `entity_topology.participation_coef`.

This distinguishes **provincial hubs** (high degree, all neighbours in same community — protagonists in a narrative) from **connector hubs** (high degree, neighbours spread across communities — structural bridges).

## 3. Implementation

### 3.1 Module location

`ml-services/app/topology.py`:

```python
def compute_communities(g: igraph.Graph, computation_version: int) -> dict[str, tuple[int, float]]:
    """
    Compute Leiden communities + participation coefficients.

    Returns: dict mapping entity_id to (community_id, participation_coef).
    """
    seed = compute_seed(computation_version)
    partition = leidenalg.find_partition(
        g,
        leidenalg.ModularityVertexPartition,
        seed=seed,
        n_iterations=2,
    )
    membership = partition.membership  # list[int] parallel to vertex order
    
    # Reassign community IDs by size desc + UUID tiebreak (deterministic)
    canonical_ids = _canonicalise_community_ids(membership, g)
    
    # Compute participation coefficient
    participation = _compute_participation(g, canonical_ids)
    
    return {
        g.vs[i]['name']: (canonical_ids[i], participation[i])
        for i in range(g.vcount())
    }
```

### 3.2 Write-back

Per `23.1` §3.2 — the community columns merge into the unified upsert.

```sql
UPDATE entity_topology
SET community_id = $1,
    participation_coef = $2,
    computed_at = NOW(),
    computation_version = $3
WHERE entity_id = $4;
```

(Bulk variant via parameterised array.)

### 3.3 Read patterns

- `GET /api/communities/:community_id` — returns the entity list for a community (lightweight, similar to `/api/components/:component_id` from `23.1`)
- `GET /api/entities?community_id=X` — entities filtered by community
- `SELECT participation_coef FROM entity_topology WHERE participation_coef > 0.5 ORDER BY pagerank DESC` — connector hubs ranked by importance

### 3.4 Reasoning agent prompt integration

The reasoning agent's patrol-mode prompt is extended to include community membership context for the entity under investigation:

> "Entity [X] is in community [N] of size [S], with participation coefficient [P]. The community contains [list of top-3 most-central entities]."

This shipping with the bead. The exact prompt wording is determined during implementation — design only commits to the data contract.

## 4. Verification

### 4.1 Manual checks

- After `topology/compute` on an empty graph: no rows written; no error
- After compute on a single entity: one row, `community_id=0`, `participation_coef=NULL` (no neighbours to compute against)
- After compute on a known multi-cluster corpus (`synthetic-10k` with `cluster_count=5`): community count ≈ 5 (Leiden may merge or split based on internal modularity, but should be in the 3–10 range)
- After re-running compute with no graph change: identical `community_id` values

### 4.2 Automated tests

Test file `platform/src/test/harness/topology-communities.test.ts`.

- **Empty graph:** no rows.
- **Single entity:** community_id=0, participation_coef=NULL.
- **Two disconnected entities:** two communities, each size 1.
- **Star graph (1 hub, 4 leaves):** depending on internal modularity, may be one community (if leaves are not further structured) — test asserts a community count of 1.
- **Two well-separated clusters (5 entities each, dense within, sparse between):** two communities, each size 5. The single inter-community edge produces participation_coef > 0 for its endpoints.
- **Communities respect components:** disconnected entities cannot share a community.
- **Determinism:** running compute twice produces identical community_id assignments.
- **Participation coefficient correctness:** triangle within a single community → P=0 for all three vertices. A vertex in community A with one edge into community B and three within → P > 0.
- **Resolution sensitivity:** with default γ=1.0, dense corpora (frankenstein) produce 2–5 communities; sparse corpora may produce more singletons. Test asserts plausible range, not exact count.
- **Snapshot benchmark:** `synthetic-10k` produces a community count proportional to the generator's `cluster_count` parameter.

## 5. Benchmark

### 5.1 Acceptance thresholds

Leiden via leidenalg + igraph is O(m log n) typical.

| Graph size | Target | Hard cap |
|---|---|---|
| 100 entities | < 50 ms | 200 ms |
| 1 000 entities | < 800 ms | 3 000 ms |
| 10 000 entities | < 8 000 ms | 15 000 ms |

Targets revised per cold-eyes review W7. Leiden via leidenalg + igraph at 10k vertices / ~30k edges typically runs 2–8 s; original 4 s target was optimistic. Master `23` §5.1 budget (12 s end-to-end target / 30 s hard cap) accommodates this.

These cover `compute_communities(g)` plus participation-coefficient computation in isolation.

### 5.2 Baseline reports

Under `platform/src/test/data/phase2-topology/benchmark-reports/communities/`:

- `synthetic-1k-communities.json`
- `synthetic-10k-communities.json`
- `frankenstein-10chunks-communities.json`
- `mixed-narrative-technical-1k-communities.json`

Each: `{snapshot_name, total_entities, community_count, modularity_score, largest_community_size, smallest_community_size, mean_participation_coef, elapsed_ms}`.

### 5.3 What we measure over time

- **Modularity score** indicates community quality. < 0.3 means the graph doesn't have strong community structure; 0.3–0.7 typical for natural graphs; > 0.7 unusual but not wrong.
- **Community count drift** between regenerations of the same corpus signals reconciliation behaviour change.
- **Participation distribution** is a histogram per snapshot. Heavy right tail (many high-P entities) suggests poorly-separated communities. Heavy left tail (many P=0 entities) suggests well-isolated communities.
- **Resolution parameter sweep** (offline experiment, not in benchmark): re-run compute with γ ∈ {0.5, 0.75, 1.0, 1.5, 2.0} and record community count + modularity. Surfaces whether γ=1.0 is a good default. Triggered manually, not in CI.

## 6. Edge cases

| Case | Expected behaviour |
|---|---|
| Empty graph | No rows. |
| Single entity | community_id=0, participation_coef=NULL. |
| Two disconnected entities | Two communities of size 1. |
| Disconnected components | Each component gets one or more communities; communities never span components. |
| Resolution limit (very dense graph with small subcommunities) | Leiden may merge small subcommunities. Documented limitation; unlikely at our scale. |
| Community of size 1 (singleton, zero-degree vertex) | participation_coef = NULL (no neighbours to compute against). The `_compute_participation` helper explicitly returns `None` for zero-degree vertices; insertion writes NULL. (Cold-eyes review W5 contract.) |
| Entity with all neighbours in same community | participation_coef = 0.0 (the value, not NULL — distinguishes "computed and zero" from "couldn't compute"). |
| Entity with neighbours in many different communities | participation_coef approaches 1. |
| Self-referential fact | Excluded from graph; no community contribution. |
| Expired fact | Excluded; community structure reflects active edges only. |
| same_as link | Counts as edge in community detection. Two same_as-linked entities will tend to share a community (high modularity). |
| Cascade-delete | ON DELETE CASCADE removes row; next compute resyncs community structure. |
| Concurrent compute | Per `23` §8.1, short-circuits. |
| Leiden seed mismatch (manual override) | Identical seed → identical communities. Different seed → different ID labels (but same community structure modulo permutation). |

### 7.2 Evolution signals

- Modularity drops sharply on a regenerated LLM snapshot — extraction or reconciliation produced denser cross-community edges
- Community count diverges from generator's cluster_count by > 50% — signal that the participation coefficient or resolution parameter need attention
- Real corpus shows community sizes wildly different from fixture coverage — extend fixtures
- Resolution parameter sweep (offline) suggests γ ≠ 1.0 is consistently better — propose tuning

### 7.4 Forward evolution

- **Hierarchical communities** — Leiden returns a hierarchy by default. Phase 2 stores only the leaf level. Future viz could exploit the full hierarchy.
- **Community-level statistics** — per-community fact density, predicate diversity, dominant entity types. Out of scope for Phase 2; would extend `graph_stats` or add a `community_stats` table.
- **Cross-community edges as bridge candidates for Phase 4** — entities at high participation_coef in *different* communities of *different* components are naturally high-priority candidates. Phase 4's cross-cluster generator design references this.
