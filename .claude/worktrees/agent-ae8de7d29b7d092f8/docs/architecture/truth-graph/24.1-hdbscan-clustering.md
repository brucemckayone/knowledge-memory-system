## 1. Purpose

**Question it answers:** Which entities live in similar parts of meaning-space?

Each entity has a centroid in 768-dim semantic space (`entity_meta.centroid`, computed as the mean of its source-memory vectors). HDBSCAN finds dense neighbourhoods in that space without requiring the cluster count to be specified — and crucially, it returns a "noise" label for entities that don't belong to any dense cluster.

The output complements Leiden community detection (`23.4`):
- **Leiden community** = "these entities are connected by graph edges"
- **HDBSCAN cluster** = "these entities live in similar parts of meaning-space"
- The two often agree (entities in the same source document tend to be both edge-connected and semantically similar). Disagreements are interesting.

Three concrete uses:
1. **Drift detection (`24.2`) compares against this clustering's `centroid_snapshot`.** Without HDBSCAN there's no snapshot to compare against.
2. **`graph_stats.embedding_cluster_count`** (Phase 1, NULL until this ships) is filled here.
3. **Phase 4 cross-cluster generator** uses HDBSCAN cluster IDs as one of its bridge-candidate signals — entities in different graph components AND different embedding clusters are weak candidates; entities in different graph components but the same embedding cluster are strong candidates.

## 2. Design

### 2.1 Algorithm

HDBSCAN (Hierarchical Density-Based Spatial Clustering, Campello-Moulavi-Sander, PAKDD 2013). Properties that matter for us:

- **No `k` required.** Cluster count is determined by data density.
- **Variable-density clusters.** Different parts of the space can have different densities; HDBSCAN handles both.
- **Noise label.** Entities outside any dense neighbourhood get `cluster_id = -1`. This is signal, not failure.
- **Soft cluster probabilities.** Each entity's `cluster_probability ∈ [0, 1]` says how confidently it belongs to its assigned cluster. Useful for downstream filtering.

Implementation: `hdbscan` Python package (the reference). Cosine distance metric (since centroids are direction-meaningful, not magnitude-meaningful, in nomic-embed-text space).

### 2.2 Hyperparameters

Three to tune:

- **`min_cluster_size`** — smallest valid cluster. Default 5. Entities in clusters smaller than this get noise label. For our typical scale (1k+ entities), 5 is reasonable: clusters smaller than 5 don't carry enough signal to be operationally useful.
- **`min_samples`** — controls how conservative the clustering is. Default = `min_cluster_size`. Higher values produce more noise; lower values produce more (but possibly smaller) clusters.
- **`metric`** — cosine for our 768-dim normalised centroids.

These are exposed via env vars (`HDBSCAN_MIN_CLUSTER_SIZE`, `HDBSCAN_MIN_SAMPLES`) for tuning. Changes bump `computation_version` and trigger backfill.

### 2.3 Centroid snapshot — the master §10 lock

Per master §10 centroid-lifecycle lock (cold-eyes review B2 fix): HDBSCAN reads the **live** `entity_meta.centroid`, then writes a **snapshot** of that centroid into `entity_clusters.centroid_snapshot` at the moment of clustering. The snapshot is what drift detection compares against.

This decouples cluster IDs from live centroid drift: re-running clustering produces (typically) the same cluster_id for the same entity, while the entity's live centroid may have moved. The snapshot is "where this entity was last clustered." Drift = cosine(live, snapshot).

### 2.4 Cluster ID assignment

HDBSCAN's raw output uses arbitrary cluster IDs starting from 0 (and -1 for noise). We re-canonicalise to:
- ID 0 = largest cluster
- ID 1 = second largest, etc.
- ID -1 = noise (preserved verbatim)

Tiebreak by smallest-member-UUID, mirroring `23.1` and `23.4`. This makes cluster IDs stable across compute runs on the same data.

**Input ordering enforcement (cold-eyes review W1):** HDBSCAN is sensitive to input row order in the mutual-reachability graph construction. The export query MUST use `ORDER BY entity_id ASC`:

```sql
SELECT entity_id, centroid FROM public.entity_meta
WHERE centroid IS NOT NULL
ORDER BY entity_id ASC;
```

The dict insertion order in the Python sidecar then preserves canonical order. The §4.2 determinism test runs compute twice with rows shuffled (insertion order varied via random `INSERT` ordering between computes) and asserts identical cluster_id outputs.

### 2.5 graph_stats backfill

After clustering completes, the routine writes back to the singleton `graph_stats`:
- `embedding_cluster_count = COUNT(DISTINCT cluster_id) WHERE cluster_id != -1`
- `mean_intra_cluster_distance` = average cosine distance of each entity to its cluster's centroid (excluding noise)
- `mean_inter_cluster_distance` = average cosine distance between cluster centroids (excluding noise)
- `cluster_columns_version` = current `computation_version`

Per `22` §7.4, this is the Phase 3 contract for filling the previously-NULL cluster columns.

## 3. Implementation

### 3.1 Module location

`ml-services/app/semantic_clustering.py`:

```python
import hdbscan
import numpy as np

def compute_hdbscan(
    centroids_by_id: dict[str, np.ndarray],
    min_cluster_size: int = 5,
    min_samples: int = 5,
) -> dict[str, ClusterAssignment]:
    """
    Run HDBSCAN over entity centroids.
    
    Returns: dict mapping entity_id to (cluster_id, cluster_probability, snapshot).
    """
    if len(centroids_by_id) < min_cluster_size:
        # Too few entities to cluster meaningfully
        return {eid: ClusterAssignment(-1, None, vec) for eid, vec in centroids_by_id.items()}
    
    entity_ids = list(centroids_by_id.keys())
    matrix = np.array([centroids_by_id[eid] for eid in entity_ids])
    
    clusterer = hdbscan.HDBSCAN(
        min_cluster_size=min_cluster_size,
        min_samples=min_samples,
        metric='cosine',
    )
    raw_labels = clusterer.fit_predict(matrix)
    raw_probs = clusterer.probabilities_
    
    # Canonicalise IDs (size desc, UUID tiebreak)
    canonical_labels = _canonicalise_cluster_ids(raw_labels, entity_ids)
    
    return {
        entity_ids[i]: ClusterAssignment(
            cluster_id=canonical_labels[i],
            cluster_probability=float(raw_probs[i]) if canonical_labels[i] != -1 else None,
            snapshot=matrix[i],
        )
        for i in range(len(entity_ids))
    }
```

### 3.2 Write-back

```sql
INSERT INTO entity_clusters (entity_id, cluster_id, centroid_snapshot, cluster_probability, cluster_size, computation_version)
VALUES ($1, $2, $3, $4, $5, $6)
ON CONFLICT (entity_id) DO UPDATE SET
  cluster_id = $2,
  centroid_snapshot = $3,
  cluster_probability = $4,
  cluster_size = $5,
  computed_at = NOW(),
  computation_version = $6;
```

`cluster_size` is denormalised (count of entities sharing this `cluster_id`). Updated in the same transaction.

### 3.3 Read patterns

- `SELECT * FROM entity_clusters WHERE cluster_id = $1` — entities in a given cluster
- `SELECT * FROM entity_clusters WHERE cluster_id = -1` — noise entities (semantic outliers)
- `SELECT entity_id, cluster_probability FROM entity_clusters WHERE cluster_probability < 0.5` — low-confidence cluster members (boundary cases)
- Joined with `entity_topology`: `WHERE community_id != cluster_id` — entities where graph community and embedding cluster disagree (interesting candidates for cross-cluster bridging)

## 4. Verification

### 4.1 Manual checks

- After compute on a graph with all-NULL centroids: `entity_clusters` empty; no error
- After compute on `synthetic-10k` (cluster_count=5): HDBSCAN reports ~5 clusters (may merge tightly-overlapping modes)
- `graph_stats.embedding_cluster_count` matches the count from `entity_clusters`
- Re-running compute on the same data produces identical cluster_id assignments

### 4.2 Automated tests

Test file `platform/src/test/harness/hdbscan-clustering.snapshot.test.ts` (snapshot-using suite per `28` §3.6 — runs serially).

- **Empty centroid set:** clustering skipped; entity_clusters empty.
- **All centroids identical:** one cluster containing all entities, OR all noise depending on `min_cluster_size` (assert correct behaviour for both edge cases).
- **Two well-separated clusters:** HDBSCAN finds two clusters; canonical_id 0 = larger, 1 = smaller.
- **Noise entities at the boundary:** entities far from any cluster get `cluster_id = -1`. `cluster_probability` is NULL for them.
- **Determinism:** running compute twice produces identical cluster_id assignments (modulo identical input).
- **Snapshot stability:** `centroid_snapshot` matches the live `entity_meta.centroid` *at the moment of clustering*. After live centroid changes (simulated), snapshot remains the old value (until next clustering).
- **graph_stats backfill:** after clustering, `graph_stats.embedding_cluster_count`, `mean_intra_cluster_distance`, `mean_inter_cluster_distance`, `cluster_columns_version` are populated.
- **Hyperparameter sensitivity:** running with `HDBSCAN_MIN_CLUSTER_SIZE=10` vs `=5` produces fewer / more clusters. Test asserts directional change.
- **Cluster size denormalisation:** every entity's `cluster_size` matches `COUNT(*) WHERE cluster_id = entity.cluster_id`.
- **Snapshot benchmark:** `synthetic-10k` produces a cluster count consistent with generator's `cluster_count`.

### 4.3 Acceptance criteria for `bd close`

- All §4.2 tests pass
- Manual checks pass
- Benchmark report committed
- `graph_stats` cluster columns correctly backfilled (matching the consistency check in `22` §7.4)
- Bridge pairs from `synthetic-10k` ground truth are placed in *different* HDBSCAN clusters (the generator's contract — verified as part of acceptance)

## 5. Benchmark

### 5.1 Acceptance thresholds

| Graph size | Target | Hard cap |
|---|---|---|
| 100 entities with centroids | < 100 ms | 500 ms |
| 1 000 entities with centroids | < 800 ms | 3 s |
| 10 000 entities with centroids | < 5 s | 15 s |

HDBSCAN scales O(n log n) with mutual-reachability distance computation, where n = entities with centroids.

### 5.2 Baseline reports

Under `platform/src/test/data/phase3-clustering/benchmark-reports/`:

- `synthetic-1k-hdbscan.json`
- `synthetic-10k-hdbscan.json`
- `frankenstein-10chunks-hdbscan.json`
- `mixed-narrative-technical-1k-hdbscan.json`

Each: `{snapshot_name, total_entities_with_centroids, cluster_count, noise_count, noise_rate, mean_cluster_probability, largest_cluster_size, smallest_cluster_size, elapsed_ms}`.

### 5.3 What we measure over time

- **Cluster count** vs corpus size — should grow sub-linearly (more data → more topics, but with saturation)
- **Noise rate** — should be low (< 20%) for well-clustered corpora; high noise on dense graphs signals hyperparameter mistuning
- **Bridge pair separation** — the synthetic generator places bridge-pair entities in different cluster modes; HDBSCAN should always assign them to *different* clusters. If bridge pairs land in the same cluster, the synthetic generator's mode separation is too small (parameter mistune)

## 6. Edge cases

| Case | Expected behaviour |
|---|---|
| All entity_meta.centroid IS NULL | Empty entity_clusters; no error. |
| Single entity with centroid | cluster_id = -1 (singleton can't form cluster < min_cluster_size). |
| Two identical centroids | Both in same cluster (size 2) if min_cluster_size ≤ 2; else both noise. |
| All centroids identical | One cluster with all entities, OR all noise (depending on min_cluster_size). |
| Centroid is a zero vector | Treated as a valid point; HDBSCAN handles. (Cosine distance to zero is undefined; HDBSCAN normalises internally.) |
| Cluster of exactly min_cluster_size | Becomes a valid cluster (boundary). |
| Hyperparameter change between computes | New compute uses new params; previous cluster IDs likely change; cluster_id is not stable across param changes. |
| Concurrent compute | Rejected via status pattern from `23` §8.1 extended to clustering. |
| Cascade-delete | ON DELETE CASCADE removes row; next compute resyncs. |
| graph_stats backfill failure (rare) | Compute succeeds; backfill is wrapped in try/catch; cluster_columns_version not bumped on failure. |

### 7.2 Evolution signals

- Cluster count diverges from `synthetic-10k`'s `cluster_count` parameter > ±50% — HDBSCAN params or generator params need attention
- Noise rate > 30% on a benchmark corpus — `min_cluster_size` too high
- Bridge pairs land in same HDBSCAN cluster — generator's mode separation too small (see `28` §3.3 step 6 verification)
- Real corpus produces a cluster shape no fixture covers — extend

### 7.3 "Done enough"

- All §4.2 tests pass
- Benchmark reports for all four snapshots
- `graph_stats` cluster columns backfill consistency verified
- Bridge pair separation verified on `synthetic-10k`
- No upstream regressions

### 7.4 Forward evolution

- **Hierarchical clustering output** — HDBSCAN produces a tree; we currently store leaves only. Future viz / UX could surface the full tree.
- **Per-cluster summarisation by LLM** — produce a one-line description per cluster (e.g. "characters in Walton's letters", "MISRA pointer-aliasing rules"). Out of scope for Phase 3; would extend `entity_clusters` with a `cluster_label` column or a sibling table.
- **Cluster-level fact density / predicate diversity** — analogous to `graph_stats` but per-cluster.
