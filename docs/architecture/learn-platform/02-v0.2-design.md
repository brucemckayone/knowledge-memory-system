# v0.2 — Adaptive Surfaces & Interactive Content

**Status:** Design phase. Implementation tracked under beads epics.
**Depends on:** v0.1 MVP scaffold (shipped).
**Goal:** Turn the MVP into a system that proactively analyses, surfaces, generates, and adapts — using the graph as its substrate at every step.

---

## What we're adding

Six work-streams, one beads epic each, mostly parallelizable after Phase 1 lands:

| Phase | Epic | Theme | Depends on |
|-------|------|-------|------------|
| 1 | Background Patrol Layer | Foundation — cron-driven analysis writes insights to a feed | — |
| 2 | Dashboard & Discovery | Surface — the new home page, surfaces what the patrol found | Phase 1 |
| 3 | Interactive Content Framework | Capability — Preact + htm + component library | — (parallel) |
| 4 | Dynamic Component Generation | Power — agents emit components inline | Phase 3 |
| 5 | Lesson Evolution | Personalisation — chat-edited per-learner overlays, notes, highlights | Phase 3, 4 |
| 6 | Cross-Course Intelligence | Synthesis — same-as detection across courses, generated articles | Phase 1 |

The first phase to ship establishes the patrol cron and the insights feed. Everything else hangs off either that or the component framework.

## Phase 1 — Background Patrol Layer

**Why:** Nothing in v0.1 runs unless the user clicks something. The system can't *surface* anything without a process that thinks while you're not there.

**What we add:**
- `insights` table on the learn server SQLite:
  ```
  insights (
    id, type, title, content_md, importance,
    related_entity_ids JSON, related_course_ids JSON,
    related_fact_ids JSON, related_section_ids JSON,
    actionable_url, created_at, dismissed_at, viewed_at
  )
  ```
- `patrol_runs` table — log of every patrol invocation with stats, for observability.
- A cron-driven patrol agent (default interval: 30 min, env-configurable, off by default in dev).
- The patrol agent is a single Claude `-p` invocation with MCP tools that:
  - Calls `get_struggle_areas` and `get_decay_candidates` (new MCP tool — uses Nmemo confidence + last_seen)
  - Calls `find_cross_course_overlaps` (new MCP tool — uses same-as detection in Nmemo)
  - For high-priority gaps, calls Nmemo's `analyze_blast_radius` to score impact
  - Writes 0-N insights via `write_insight` MCP tool (idempotent on (type, related_entity_ids))
- One cycle is bounded: max 5 insights written per run, max 12 MCP turns.

**Insight types** (the patrol's emergent vocabulary, not a fixed enum — we let it grow):
- `decay_warning` — concept hasn't been reinforced, fading
- `cross_course_link` — same concept seen in two courses
- `prerequisite_gap` — newly detected gap blocking downstream concepts
- `pattern_emerging` — recurring learning pattern crystallising in Graph C
- `synthesis_candidate` — dense cluster of concepts ready for an article
- `contradiction_detected` — opposing understandings logged in different sessions

**MCP tools added:**
- `get_decay_candidates(threshold_days)` — concepts with low last_seen recency and high prior confidence
- `find_cross_course_overlaps()` — same-as detection across courses
- `find_dense_clusters(min_size)` — concept clusters connected by recent learner activity
- `write_insight(type, title, content_md, related_*_ids, importance)` — append-only

**Cron service:** simple `setInterval` in the learn server's main process. No queue infra. State held in `patrol_runs.last_run_at`.

## Phase 2 — Dashboard & Discovery

**Why:** v0.1's home is a course list. v0.2's home is a personalised dashboard that uses the graph + insights feed.

**What we add:**
- New `/api/dashboard` endpoint that returns a composed bundle:
  - "Jump back in" — most recent quiz_attempt + chat_message, plus the section/course they were in
  - Daily quiz card — adaptive question pulled by `get_next_question_anywhere` (across all courses, weighted by gap impact)
  - Daily flashcards — top N decay candidates, formatted as flashcards
  - Insights feed — recent undismissed insights ordered by importance + recency
  - Cross-course connections — concept entities that appear in 2+ courses with at least one same-as link
  - Graph snapshot — total concepts, total facts, recent growth (e.g. "+5 concepts this week")
- New Dashboard view in the frontend, replaces Courses as the home tab.
- Daily flashcard view — flip-card UI, swipe to log "knew it" / "didn't know it" — feeds back into the graph.

**Flashcards** are a new entity:
```
flashcards (
  id, concept_entity_id, course_id NULL,
  front_text, back_text, hint_text,
  generated_at, generation_source
)
```
Flashcards are generated by a flashcard-generator agent on demand (when the patrol marks a decay candidate, or when the user opens daily review).

**Adaptive selection.** The "next question anywhere" tool ranks across all courses by:
- Concept's blast radius score (gaps blocking the most downstream)
- Recency of last attempt (decay-weighted)
- Lower scores get higher priority

## Phase 3 — Interactive Content Framework

**Why:** Plain markdown with embedded code blocks is dull. Interactive components are how you actually learn complex topics.

**Technical decision:** Add **Preact + htm** to the frontend. ~3kb gzipped, JSX-like syntax via tagged template literals, no build step. Loaded from CDN alongside `marked`. Vanilla-JS-feel preserved (no toolchain, no transpiler) but real component composition unlocked.

**Component library** — fixed set of well-tested types:
- `<Callout type="info|warning|insight|takeaway">` — styled boxes
- `<CodeRunner lang="js" code="...">` — embedded sandboxed JS evaluator (uses iframe sandbox)
- `<Mermaid src="...">` — Mermaid diagrams
- `<SvgFigure src="...">` — agent-generated raw SVG (sandboxed for safety)
- `<StepThrough steps={[...]}>` — animated walkthrough; click "Next" to advance
- `<FlashcardDeck cards={[...]}>` — quiz/review cards inline
- `<ConceptMap nodes={[...]} edges={[...]}>` — small interactive graph
- `<Highlight onAsk>` — wraps content, click reveals "explain / example / why" actions

**Lesson document format.** Lessons become structured JSON documents:
```json
{
  "blocks": [
    {"type": "markdown", "content": "## Why this matters\n\n..."},
    {"type": "component", "kind": "Mermaid", "props": {"src": "..."}},
    {"type": "markdown", "content": "..."},
    {"type": "component", "kind": "StepThrough", "props": {...}}
  ]
}
```
The lesson generator agent (existing) is updated to produce this structure. Older string-only lessons still render (treated as a single markdown block).

**Renderer:** a single Preact `<LessonRenderer>` that walks the blocks, renders markdown with `marked`, and dispatches components by `kind` to the library.

**Safety:** SVG and HTML from agents are sanitised. Code blocks run in a sandboxed iframe with no network, no DOM access to the parent.

## Phase 4 — Dynamic Component Generation

**Why:** Static lesson components are good. Live, contextual components are better. When the chat tutor explains something, it should be able to *show*, not just *tell*.

**What we add:**
- A **component-generator agent** orchestrated by the chat tutor.
- New MCP tool: `generate_component(kind, context)` — invokes the component-gen agent with the requested component kind (Mermaid diagram, SVG figure, code example, step-through animation, etc.)
- The chat tutor's response becomes a structured document (same blocks format as lessons), not plain text.
- The chat UI renders components inline — interactive Mermaid, runnable code, step-through animations.
- "Save to lesson" button on each generated component — promotes it into the per-learner lesson overlay (Phase 5).

**The chat-as-orchestrator pattern:** the user says *"I don't get how reverse-in-place works"*. The chat tutor's MCP loop:
1. `get_learner_understanding("reverse linked list")` — confirms it's weak
2. `generate_component({kind: "StepThrough", ...})` — produces a 6-step animated walkthrough
3. Returns a chat response with the markdown explanation interleaved with the component spec.
4. UI renders the chat message including the live component.

The component-generator agent uses Sonnet (it needs to produce valid SVG/JSON), short timeout (~60s per component), and is hard-bounded — one component per chat turn unless the chat agent explicitly asks for more.

## Phase 5 — Lesson Evolution

**Why:** Two ideas: (a) the canonical course content shouldn't change for everyone when one learner asks for a clarification; (b) the AI's edits sometimes make things worse, so we need a way back.

**What we add:**
- **Per-learner lesson overlays** — when the chat tutor or learner edits a section, the change is stored in `lesson_overlays(learner_id, section_id, blocks JSON, version, created_at)`. Canonical lesson stays untouched.
- **Versioning** — every regeneration adds a row. Learner can view history and revert.
- **Highlight + popover annotations** — frontend captures highlight selection, shows a small action menu (Explain / Example / Why does this matter / Take a note). Each action calls a tiny on-demand explainer agent that returns a popover-sized response.
- **Notes** — `notes(id, learner_id, section_id, anchor_text, content_md, promoted_to_graph)`. By default notes are private. A "Promote to graph" button calls `record_understanding` or `record_confusion` on the learner graph — the user explicitly chooses what's signal.

**MCP tools added:**
- `edit_lesson_section(section_id, edit_op)` — chat-driven lesson modifications. `edit_op` is one of: `insert_block`, `replace_block`, `append_clarification`, `add_example`. Always writes to the overlay, never canonical.
- `revert_lesson(section_id, to_version)` — takes the learner back N versions.

## Phase 6 — Cross-Course Intelligence

**Why:** This is where the graph really pays for itself. A user takes a JavaScript course and a Rust course; the system notices `closures` appears in both, recognises that what JS calls a `closure` and what Rust calls a `move closure` are the same concept (via Nmemo's same-as detection), and surfaces this to the learner.

**What we add:**
- **Connection-finder agent** (runs on patrol): walks Nmemo's `same_as_links` and `merge_candidates` between concept entities that appear in different courses. For each non-trivial overlap, generates a `cross_course_link` insight.
- **Article generator agent** — when patrol detects a dense cluster (5+ concepts the learner has touched recently across multiple courses), generates a synthesis article that ties them together. Stored as a special "synthesis" entity, surfaced on the dashboard.
- **Bridge UI element** — at the top of any section, if there's a cross-course link to that concept, show a small "you've seen this before in [Course X]" link.

**The same-as use case** is novel here because it's NOT just deduplication — it's pedagogical. Two concepts being the same is a teaching opportunity, not a data-cleanup problem.

## Crosscutting concerns

**Frontend stack upgrade.** Loading Preact + htm + marked + mermaid from CDN. No build step. Total weight ~80kb gzipped. State management: signals from `@preact/signals`. No router needed (single page, view switching by state).

**Database growth.** New tables: `insights`, `patrol_runs`, `flashcards`, `lesson_overlays`, `lesson_versions`, `notes`. SQLite handles all of this without breaking a sweat at MVP scale.

**Cron.** Simple `setInterval` started from `index.ts`. On each tick, check `patrol_runs.last_run_at` against the configured interval. If due, kick off a patrol. Skip if a patrol is already in flight (mutex via in-process flag). Add a `/api/patrol/run-now` endpoint for manual triggers and testing.

**Failure handling.** Insights are best-effort. A failed patrol logs and skips. A failed component generation falls back to "let me describe this in text" in the chat tutor. No feature should hard-block on background analysis.

**Observability.** New `/api/patrol/runs` endpoint returns recent runs with status, insights produced, MCP calls made, duration. Visible in a dev panel for inspection.

## Order of work

The critical path:

```
Phase 1 (patrol foundation) ──────┬──→ Phase 2 (dashboard)
                                  └──→ Phase 6 (cross-course)

Phase 3 (component framework) ────┬──→ Phase 4 (dynamic components)
                                  └──→ Phase 5 (lesson evolution)
```

Phase 1 and Phase 3 can run in parallel — they share no dependencies. Phase 2 depends on Phase 1's insights. Phase 4 depends on Phase 3's component library. Phase 5 depends on both Phase 3 and Phase 4. Phase 6 depends on Phase 1's patrol.

Suggested implementation order: **1 → 3 → 2 → 4 → 5 → 6**. This delivers visible value early (dashboard with patrol-driven insights) while building up the component framework needed for the heavier features.

## Out of scope (explicit)

- Multi-learner. Single learner only.
- Auth or accounts.
- Mobile-specific UI.
- Offline support.
- Course marketplace, sharing, exporting courses.
- Voice input/output.
- Grading or external assessment integrations.
