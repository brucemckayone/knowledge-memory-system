### nmemo-2yv.84 — topology / clustering / drift auto-triggers

- **Lesson:** Module-cached config (`config = loadConfig()` at module init) plus a fire-and-forget HTTP target (here: `http://127.0.0.1:${config.PLATFORM_PORT}/api/...`) creates a hard-to-test seam. A direct `process.env` override at call time has the right runtime semantics but makes prod code think test-mode. A small explicit `_setComputeUrlPortForTesting(port)` seam (underscore-prefixed export, null-or-number override) is the cheapest honest middle: production runs through `config`; tests inject the stub server's bound port without leaking env-var tweaks. Same shape worked for `scheduler.ts`. Worth the four extra lines.
- **Surprise:** The bead's locked Decision specified a `derived_freshness` table with "On fact insert, increment facts_since_compute. When >= threshold, fire compute fire-and-forget." Initial instinct was to put the whole detect-and-fire logic in a single PL/pgSQL trigger. Pulled back — PL/pgSQL has no business calling HTTP endpoints (pg_net / pl/pythonu would be required). The split: DB trigger increments only; platform-layer `maybeFireFactThresholdCompute()` does the atomic compare-and-reset + fires. The atomic reset (UPDATE ... WHERE facts_since_compute >= threshold RETURNING) deduplicates parallel-inserter races without an advisory lock — the second inserter sees `facts_since_compute = 0` and returns 0 rows from RETURNING.
- **Pattern noted:** Time-driven cadences are a real third category alongside DB-reactive and post-event chains. Doc 32 §3 already had the `Scheduled` taxonomy slot; this bead populated it. The single `scheduler.ts` home for all `node-cron` jobs (drift today, `.71` reasoning patrol next, etc.) keeps the lifecycle (`startScheduler`/`stopScheduler` + SIGTERM hook) in one place — every additional time-driven cadence registers there, not in its own ad-hoc setInterval.
- **Pattern noted:** The bead acceptance bullet "Concurrency: all auto-triggered computes go through /api/{topology,clustering,drift}/compute and respect .87's race-window fix" was satisfied for free because every trigger here POSTs to the existing HTTP route. Routing all auto-triggers through the same HTTP endpoints the manual debug paths use means one concurrency story to maintain. This is the same principle as "the freshness gate stays satisfied because both compute kinds fire together" — fewer code paths == fewer concurrency arguments to rebuild.

### nmemo-2yv.63 — merge_entities() FK violation on contradictions (T13 + post-merge integrity)

- **Lesson:** When a later migration adds a FK from a new table back to a long-established parent (here: `contradictions.entity_id → entities(id)` in mig 011) WITHOUT an ON DELETE clause, the parent's merge/delete logic must be updated in the SAME landing. PostgreSQL defaults to NO ACTION; the merge SQL in mig 005 (predating mig 011) had no reason to know about a future FK. Audit pattern: whenever adding a FK to entities, run `git grep "DELETE FROM public.entities"` to check the merge_entities() body needs a re-point step.
- **Surprise:** The bead's recommendation was "re-point rather than CASCADE" — preserving the contradiction trail across merges. But the partial UNIQUE INDEX `idx_contradictions_unique_active` (covering `entity_id` as one of its keys) means a naive `UPDATE contradictions SET entity_id = target_id` can violate the index if both source and target carry an unresolved contradiction with the same (type, fact_a, fact_b, edge_a, edge_b). The dedup DELETE has to mirror the index expression EXACTLY — same COALESCE sentinel UUID and same column tuple. Mis-aligning either would either over-delete or under-delete and fail the merge at the UPDATE.
- **Pattern noted:** PL/pgSQL multi-step migrations like merge_entities() are append-shaped — each "re-point step" gets bolted on. Without a discipline of "every new FK to entities triggers a paired merge-step", these accumulate as latent bugs. Worth filing a future check: a CI lint that verifies every FK with `REFERENCES public.entities` has a corresponding re-point step in merge_entities() or an explicit `ON DELETE CASCADE`/`SET NULL` clause.

### nmemo-2yv.38 — resolveContradiction transactional correctness (concurrency hardening)

- **Lesson:** Threading an optional `tx?: Tx` through mutation primitives (`expireFact`, `invalidateFact`, `expireCausalEdge`, `reviseCausalEdge`) is a clean refactor — the `runUpdate(tx)` helper used either with the passed-in tx or under a freshly-opened `db.transaction(runUpdate)` keeps the existing callers backwards-compatible while letting multi-step orchestrators (here: `resolveContradiction`) own the atomicity boundary. The exported `Tx = Parameters<Parameters<typeof db.transaction>[0]>[0]` type alias in `db/index.ts` is the cheapest way to surface drizzle-orm's transaction type without dragging in pg-core internals.
- **Surprise (caught by /code-review subagent):** Threading tx through the primitives is necessary but not sufficient for full atomicity. `expireFact` and `invalidateFact` delegate to `createCausalEvent` and `cascadeFactExpiry` AFTER their inner tx body returns — those delegations always run on the module-level `db` pool, even when the caller supplied a `tx`. If the outer tx rolls back (e.g. closing UPDATE contradictions throws), the causal_event and cascade-expired edges have already committed on separate connections and stay behind as orphans. This is the next domino — tracked as the bead's "Broader improvement note" follow-up, deferred from .38 by design.
- **Pattern noted:** When extending a primitive with an "optional outer transaction" parameter, the post-mutation side effects (audit emissions, cascade work) usually want the SAME tx-aware treatment. Not threading them is the smaller change but leaves a latent orphan-on-rollback. Whenever this pattern lands again (entity merges, etc.), thread tx ALL the way through or document the partial-atomicity explicitly. The /code-review subagent's "high-confidence" verdict on this gap is correct — the bead's locked scope just chose to defer it.

### nmemo-2yv.37 — edge-mutating contradiction resolution (T13 half-built pipeline)

- **Lesson:** When a polymorphic enum (here: `resolution_type`) dispatches through a TypeScript switch, the `default: const _exhaustive: never` pattern is what catches drift — but ONLY if every layer (DB CHECK, MCP enum, HTTP body cast, agent prompt) is also extended in lockstep. The TS exhaustiveness check protects the dispatcher, not the boundary layers above it. For new vocabulary, edit the union LAST so any layer you missed becomes a compile error against the (already-extended) switch's exhaustiveness verifier. Counter-pattern: don't edit the union first, because then the switch happily accepts unhandled values during the in-progress edits.
- **Surprise:** The bead's "Scoped fix" mentioned six layers (migration, contradictions.ts, causal-agent.ts, index.ts, reasoning_agent.py, doc 16). The seventh (HTTP body inline type union at index.ts:673-676) was visible only as a `body.resolution_type as` cast — not as a type imported from the service layer. This is a pre-existing weak-typing seam that lets the union drift silently; future hardening could replace the cast with `import type { ResolutionType }`.
- **Pattern noted:** The bead listed a "Future direction" footnote about replacing the static enum-dispatcher with a per-contradiction agent call. Option B (this bead) is a stopgap. The TOCTOU race surfaced by the code-review subagent (`expireCausalEdge` is a no-op on already-expired edges → if another path expires the edge between detection and resolution, the contradiction closes with no history row) is a known consequence of the static-dispatch design; the "Future direction" rewrite obviates it.

### nmemo-2yv.60 — resolve_candidate enum / merge_candidates CHECK alignment (T7 naming mismatch)

- **Lesson:** When a CHECK constraint enumerates vocabulary that other layers (tool schemas, agent prompts, table names) also enumerate, a divergence is silent and total — every write of the new value hits the CHECK and fails on the close path, while the upstream side-effect (here: the same_as_links row) lands via a different write path. The bug only surfaces if you check the candidate row's *post-resolution* status rather than the link table. This is a generalisable test-design lesson: when a pipeline writes to two tables and an error in one is recoverable into the other, end-to-end tests must assert *both* terminal states, not just the visible one.
- **Surprise:** The bead's Scoped fix had three steps but the third ("integration test against the DB write path") was the one carrying the regression-guard value. Steps 1 + 2 (migration + grep-for-readers) could have been done blindly with low-confidence safety; step 3 is what locks down the contract. The instinct to land migrations without an exercising test would have allowed a future revert of the CHECK to slip through unnoticed.
- **Pattern noted:** Doc 27 §2.2 already discusses 'same_as' as a training-label vocabulary. The schema CHECK in 003 predates that discussion. Whenever a vocabulary discussion lands in a design doc, run `grep "CHECK.*IN (" platform/src/db/migrations/*.sql` against the new vocabulary to detect drift early. Future work: vocabulary-alignment pass before reasoning_reports (per the bead's "Future direction" note).

### nmemo-2yv.112 — Pi bridge port default 3001 → 3099

- **Lesson:** When a bead's Scoped fix lists multiple edits and one of them is incompatible with the project's actual dev environment, prefer the smallest faithful change that satisfies the bead's *acceptance* over a literal application that introduces a regression. Here the bead asked for `"bridge": "PI_BRIDGE_PORT=3099 tsx src/services/pi-agent-bridge.ts"` in `package.json`, but inline `KEY=value cmd` syntax doesn't work in Windows cmd/PowerShell (the user's primary shell per CLAUDE.md), so `npm run bridge` would have regressed. Skipping that step was the right call because the code-default change at `pi-agent-bridge.ts:38` already satisfies the actual acceptance bullet ("npm run bridge starts the bridge on 3099 with no extra env setup needed"). Always check the bead's *acceptance contract* vs the *implementation list* — the former is the binding spec.
- **Surprise:** Bullet 5 said "deleting ml-services/.env and running make bridge + make ml works (llm.py picks up the 3099 code default)" — but deleting `.env` also strips `LLM_PROVIDER=pi`, which makes `LLM_PROVIDER` default to `claude`, which means `PiBridgeProvider` is never instantiated and the bridge-URL default never gets exercised. The bullet as literally written passes vacuously. To honour the bullet's *intent* (verify the code default), unset `PI_BRIDGE_URL` while keeping `LLM_PROVIDER=pi` and instantiate `PiBridgeProvider` directly.
- **Pattern noted:** Bullet 6 ("Port table in doc 29") referenced a doc owned by a separate bead (`.110`). This is a recurring shape in this review cycle — beads sometimes carry forward dependencies that can't be satisfied at their own implementation time. The skill should treat such bullets as "deferred to the owning bead" rather than halting acceptance.

### nmemo-2yv.98 — listCrossClusterCandidates statusFilter (sibling of .45)

- **Lesson:** When a sibling bead (.45) recently landed the same filter+paginate pattern on an adjacent query helper, the cheapest implementation is to mirror its shape *with the new bead's locked defaults*, not the sibling's defaults. Here .45 chose `['staging','candidate','provisional']` as default-unresolved; .98 locked `['candidate','staging']` specifically (drops 'provisional' from default). The bead's Decision section wins by definition — the sibling's choice is informative but not normative. Read both, follow the lock.
- **Lesson:** The `sql.join(arr.map(s => sql\`${s}\`), sql\`, \`)::text[]` idiom from .45 transplants cleanly to any helper that needs a runtime-variable status set. Reusing the exact idiom (not paraphrasing it) makes the diff trivially auditable against the prior bead. Pattern crystallised: status-filter SQL = `WHERE col = ANY(ARRAY[${sql.join(arr.map(s => sql\`${s}\`), sql\`, \`)}]::text[])`.
- **Surprise:** The bead body cited `cross-cluster-generator.ts:521-563` for the helper, but the actual lines were 596-639 (78-line drift). Line-ref drift is the same shape as .111's path drift — *symbols + behaviour* matched; the line numbers had aged. Note in PREMISE_OK rather than halt. Pattern: bead premise = symbols + behaviour, not line numbers.
- **Pattern noted:** Exposing the valid-vocabulary enum (`CROSS_CLUSTER_CANDIDATE_STATUSES`) from the service module rather than redeclaring it in the route handler keeps the source of truth single. The route imports and validates against it; when a future migration extends the CHECK constraint, only the service-layer constant changes. Same shape as .45's `DEFAULT_UNRESOLVED_STATUSES` — but exporting the FULL set (incl. 'resolved') is what the route validator needs, not just the unresolved subset.
- **Pattern noted:** A ternary like `cond ? f(x) : f(x, y)` collapses to `f(x, y-or-undefined)` when `f` has a default param — passing `undefined` to a defaulted parameter triggers the default per ES2015 spec. /simplify caught this one-liner. Worth remembering: explicit `undefined` IS the "use default" signal at the call site.

### nmemo-2yv.83 — drift-reconciliation post-compute trigger (T13 / G4 half-built pipeline)

- **Lesson:** When a bead spec includes example SQL or example payloads, the field names may be from the *consumer's* (payload-side) layer, not the *storage* (column-name) layer. The bead's `## Decision` SELECT used `source_cluster_id` (the agent's `ReconciliationDriftRequest` payload field). The actual column in `entity_drift_events` is `cluster_id_at_detection` (per 016 §3.2). Copy-pasting the bead's SQL verbatim produced a Postgres `column "source_cluster_id" does not exist`. **General rule:** when a bead author writes example SQL, treat field names in the example as conceptual; before writing the query, read the target table's schema and translate. Cheap fix, easy to miss — the test caught it immediately, but a fix landed without a test wouldn't have.
- **Surprise:** The bead's locked spec read "On agent success, the entity_drift_events row has reconciliation_run_id set referencing the agent's generated row in reasoning_reports / gardening_reports / appropriate audit table." Reading the ml-services `/reconciliation-agent/drift` endpoint (`drift.py:771-803`) showed the agent returns ONLY a `{result: str}` — it never writes to reasoning_reports or any audit table. The bead's success-path narrative was aspirational about a future where the agent self-writes audit rows. The faithful minimum-change interpretation: the platform helper writes the audit row itself, capturing the agent's text in `reasoning_reports` with `mode='patrol'` (closest legal CHECK value) and `actions_taken.source='reconciliation_drift_agent'` for disambiguation. A future bead can either add a `'drift_reconciliation'` mode (CHECK relaxation, ~5-line migration) or push the audit-write into the agent itself.
- **Pattern noted:** In fire-and-forget helpers invoked via `void helper()`, any *setup* work (dynamic imports, config resolution) MUST live inside the outer try/catch. A failure above the try escapes as an unhandled promise rejection (Node 20+ default = process death on strict mode). The sibling `triggerCrossClusterAfterCompute` (index.ts:999) already follows this — its dynamic import is inside the try at line 1001. My first cut put the dynamic import on the line above the try; code-review caught it. **Rule:** for any `export async function trigger*(...)` matching the fire-and-forget pattern, the FIRST line of the function body should be `try {` and ALL awaits live inside.
- **Pattern noted (carry-forward, deferred):** Cross-helper concurrency. `triggerCrossClusterAfterCompute` uses `pg_try_advisory_xact_lock(hashtext(LOCK_KEY))` to deduplicate overlapping invocations. The new drift-reconciliation helper does NOT (bead spec didn't require it). Two overlapping `/api/drift/compute` calls would double-invoke the LLM and orphan one of two `reasoning_reports` rows per drift event. Bead `.88` is the natural home for sweeping both helpers into a services module — at that point, also adopt the advisory lock pattern uniformly. Tracked in the bead's deferred-follow-ups note for whoever picks up `.88`.

### nmemo-2yv.87 — compute endpoints: pg_try_advisory_xact_lock replaces SELECT-then-INSERT pre-check

- **Lesson:** When replacing a SELECT-then-INSERT race-prone pattern with a transaction-scoped advisory lock, the WHOLE compute work has to live inside the same transaction — otherwise the lock releases the moment any intermediate `conn.commit()` fires. This forces a structural shift: the old pattern committed the `in_progress` row early so external observers could see the work in flight; the new pattern only commits the `completed` row at the very end, and failures roll back the entire transaction (no `failed` row persists). Module-level docstrings that described the old "marked 'failed' on rollback" behaviour become stale and need updating in the same diff. The status table changes meaning: from "in-flight + final outcomes" to "completed runs only". Anyone relying on early in-progress visibility (status endpoints, dashboards) must instead query `pg_locks`.
- **Surprise:** Both the bead spec's example SQL AND my first cut wrote the `except Exception as exc:` block, refactored to `except Exception:` (no binding), and left a stray `raise HTTPException(..., detail=f"...{exc}")` referencing the now-undefined `exc`. The dead-line wasn't reachable (preceding unconditional raise), so no linter-free runtime would surface it — but the code-review subagent caught it as F821 undefined-name in a hypothetical-future scenario where someone removes the preceding raise. **Pattern:** whenever an `except As name:` clause loses its `as name`, immediately scan the rest of the except body for surviving references to `name`. Editor multi-cursor or grep-and-replace is the safer path.
- **Pattern noted:** Postgres `pg_try_advisory_xact_lock(<integer>)` has ONE namespace across all single-argument callers — int4 widens to bigint via implicit cast. Writing "different namespace" in a comment because one caller uses `hashtext('text')` (int4) and another uses literal bigints is technically wrong; only the *values* differ, not the namespaces. The locks.py module now documents this explicitly with the int4 range upper-bound guarantee for the hashtext-derived caller vs the small bigints 1001-1003. Future bigint callers MUST stay outside int4 range or compute the hashtext literal to prove non-collision.
- **Pattern noted (carry-forward):** Three nearly-identical handler bodies (topology / clustering / drift) all wrap the same lock-acquire pattern with only the lock key constant differing. Extraction to a helper (e.g. `with acquire_compute_lock(conn, 'topology'):`) is tempting but premature — the bead's locked spec didn't call for it, and the inline shape keeps the lock-key-to-endpoint mapping explicit at every site. If a fourth caller lands in this style, extract then.

### nmemo-2yv.29 — createFact dedup branch wrapped in db.transaction for audit atomicity

- **Lesson:** When a mutation primitive already has a tx-aware sibling pattern (here: four other paths in `facts.ts` already wrap UPDATE + recordFactChange in `db.transaction(async (tx) => {...})` and thread `tx`), the cheapest test for "is this branch broken?" is to ask whether it follows the sibling shape. Reusable for any other tx-wrapped audit row that has a CHECK constraint downstream.

### nmemo-2yv.61 — reconciliation agent pipeline auto-trigger (T12 design-contract drift)

- **Lesson:** When a "documented contract" (here: the reconciliation_agent.py system prompt's "You run AFTER extraction" assertion + RECONCILIATION_AGENT_REVIEW.md's "fire-and-forget at pipeline.ts line 188" description) quietly falls out of the code over a release cycle, the doc becomes a liar but the system keeps shipping. ### nmemo-2yv.132 — Startup-validation invariants integration point

- **Lesson:** A validator wrapper that BOTH catches exceptions AND enforces a timeout is the right shape for boundary checks at startup. The pattern: `Promise.race([validator.run(), new Promise((_, reject) => setTimeout(() => reject(new Error('timeout ...')), N_MS))])` inside a try/catch that returns `{ok: false, detail: message}`. This means a validator that throws on unreachable network calls (e.g. ensureCollections throwing on Qdrant dim mismatch) AND a validator that hangs (e.g. ml-services returning a never-resolving promise) BOTH surface as a normal `ValidatorResult` with `ok: false` — no exceptions ever propagate to the aggregator. The aggregator's job becomes trivially "run them all, collect results, report".
- **Lesson:** The aggregator MUST NOT short-circuit on first failure. ### nmemo-2yv.30 — Replace PL/pgSQL merge_entities() with audited TS mergeEntities()

- **Lesson (UPDATE...RETURNING for audit-set integrity):** When a single TS function must (a) mutate a set of rows and (b) emit one audit row per mutated row, the SELECT-then-UPDATE pattern is a race seed under READ COMMITTED isolation. Between the SELECT-of-affected-ids and the UPDATE-of-same-where, a concurrent inserter can land a NEW row matching the WHERE; the UPDATE then mutates it without producing an audit row, leaving audit-set drift from mutation-set — the exact silent gap the original PL/pgSQL function had. `UPDATE ... RETURNING id` collapses both into one atomic statement; the RETURNING set is provably the mutation set. Apply this anywhere the bead's acceptance bullet specifies "every affected row gets exactly one history row" — the only way to keep that as a HARD invariant (vs best-effort) is the single-statement form. Generalises: whenever a future bead adds another "audit every mutation" service primitive, default to UPDATE...RETURNING / DELETE...RETURNING; avoid SELECT-then-mutate splits.
- **Lesson (FactEventType extension contract):** Adding a new event_type value requires lockstep edits across two layers — the TS union in `src/services/audit.ts:FactEventType` AND the DB CHECK constraint in `fact_history.valid_fact_event_type`. The Actor union is similarly co-located (mig 009 line 47-50 + audit.ts line 69-76). Pattern noted: any future audit lifecycle event should follow the same shape — extend the union LAST so any layer missing the matching DB constraint fails CI at the test-write level. The bead's locked Scoped fix correctly defined "one history row per affected fact" — translating verbatim with SELECT-then-UPDATE would have shipped the gap; the /code-review pass that surfaced the race window earned its keep here. - **Lesson (postgres.js + drizzle dual usage):** `tx.execute(sql\`...\`)` is drizzle, RETURNS the postgres.js native row shape (snake_case keys). The `unwrapRows<T>()` helper from audit.ts is the right normaliser — it handles both `Array<T>` (postgres.js direct) and `{ rows: T[] }` (some adapter paths) shapes in one cast. - **Surprise (NOW() inside a transaction = constant timestamp):** Two `recordFactChange` calls inside the same tx for the same fact (e.g. a duplicate fact that gets BOTH subject-re-pointed AND duplicate-expired in the same merge) produce fact_history rows with IDENTICAL `occurred_at` — `NOW()` returns transaction-start time, not statement-start time. ### nmemo-2yv.65 — merge_entities() dangling-UUID re-point (topology_bridges FK + reasoning_reports.entity_ids[] array)

The fix has two halves and they're separable: (i) add the FK so future drift can't accumulate, (ii) re-point in the merge transaction so the survivor inherits the bridge. ON DELETE CASCADE is the right semantic specifically because bridges are derived data (igraph.bridges() output) — a CASCADE-dropped bridge regenerates on the next gardener pass. For non-derived FK targets, the same shape would need `ON DELETE NO ACTION` + an explicit re-point step instead. **Audit pattern:** when adding a FK to `entities`, classify the holding table as derived-recomputed (CASCADE) or canonical (re-point + NO ACTION). - **Lesson (canonical-order CHECK + UNIQUE constraint forces a 4-statement re-point shape):** topology_bridges has BOTH `CHECK (source_entity_id < target_entity_id)` AND `UNIQUE (source_entity_id, target_entity_id)`. A simple `UPDATE source_entity_id = target` cannot satisfy both unconditionally — order-preserving re-points need their own UPDATE; order-violating cases must be dropped (CASCADE handles them after source DELETE); unique-clash duplicates must be DELETED before the UPDATE; self-bridges must be DELETED after the UPDATE. Four statements total: pre-delete-unique-clash → update-low-side → update-high-side → post-delete-self-bridges. Pattern mirrors same_as_links step 11 (mig 005:138-145) but adds the unique-clash pre-pass that same_as_links omits (and that .64 will need to fix for same_as_links). The order matters: pre-delete-unique-clash must come BEFORE the updates (otherwise the UPDATE violates UNIQUE); post-delete-self-bridges must come AFTER (a row where target_entity_id == sourceId AND source_entity_id == targetId is created by the high-side UPDATE on a pre-existing (targetId, sourceId) row only if both endpoints are involved — practically, the row exists pre-merge as (lower, higher) where {lower, higher} == {source, target}, and the canonical-order check on the UPDATE branches both skip it, leaving it for the post-DELETE step).
- **Lesson (array_replace for FK-impossible columns is the canonical idiom):** `reasoning_reports.entity_ids UUID[]` cannot carry an element-level FK in Postgres — array columns don't compose with REFERENCES. The merge transaction must imperatively `UPDATE ... SET entity_ids = array_replace(entity_ids, ${sourceId}::uuid, ${targetId}::uuid) WHERE ${sourceId}::uuid = ANY(entity_ids)`. The WHERE clause limits the scan via the existing GIN index; the SET re-indexes on UPDATE. No audit emission needed — `reasoning_reports` is a provenance log of agent passes, not a mutating-fact-state assertion. **Audit pattern:** grep `UUID[]` and `UUID NOT NULL DEFAULT '{}'` migrations for other array-of-entity-id columns that need the same `array_replace` treatment — `reasoning_reports.fact_ids` and `causal_edge_ids` are sibling columns in the same table (out of scope for .65 since they reference facts and edges, not entities).

The two steps appear redundant — wouldn't CASCADE alone clean up the dangling rows? It would. The reason to ALSO re-point is preservation: a CASCADE-only solution drops the bridge entirely; a re-point preserves the bridge against the survivor entity. For derived data (regenerates on next gardener pass) the cost is low, but the re-point shortens the window of "broken bridge data" from one-gardener-pass to zero. **Implication:** when a fix has a "make-the-bug-impossible" half (FK) AND a "preserve-information" half (re-point), the two are complementary, not alternatives. CASCADE catches the cases the re-point misses (canonical-order violations) and prevents future regressions; re-point preserves what can be preserved on the happy path.

### nmemo-2yv.62 — centralised prompt-safety helper for agent-writable read-back fields (T8)

- **Lesson (the helper lives at the read-into-prompt boundary, not the write boundary):** Two equally tempting designs for T8 hardening are (a) cap+sanitise at write-time (in the `update_entity_summary` tool handler, in the graph-agent PHASE 6 persist call), and (b) wrap-and-sanitise at the read-into-prompt boundary (every tool handler that returns a persisted summary/report to the agent). ### nmemo-2yv.119 — ml-client 429 + Retry-After

- **Lesson (rate-limit responses need a different sleep schedule than transient-infra responses):** The pre-bead `RETRY_STATUS_CODES = {502, 503, 504}` set lumped all retryable errors into one linear `[500, 1000]ms` backoff. 429 is semantically different — it's a *cooperative* signal from a healthy server that says "the schedule is yours to read in `Retry-After`." Retrying at 500ms when the server said `Retry-After: 5` either re-throttles (best case) or earns the caller a per-IP ban (worst case). The fix shape is one status-code-conditional branch in the retry path: only 429 consults the header; 502/503/504 keep the linear schedule. The branching is narrow enough that it doesn't justify a per-status-code dispatch table — `response.status === 429` is the only special case until a real second one appears. **Rule:** when a retry set spans semantically different error classes (transient infra vs cooperative rate-limit vs auth-rotation vs ...), the sleep policy should fork on the class, not be unified.
- **Lesson (regex-then-fallback parser shape beats `Number()`-then-`Date.parse()`):** `Retry-After` accepts two formats — a non-negative integer-seconds count OR an HTTP-date string. The naive shape `const n = Number(h); if (Number.isFinite(n)) ... else Date.parse(h)` is wrong because `Number("Wed, 21 Oct 2026 GMT")` is `NaN` (fine) but `Number("2026")` is `2026` (also fine — and `Number.isFinite(2026)` is `true`), and the function would interpret a date-year string as 2026 *seconds*. The cure is a regex guard `^\d+(?:\.\d+)?$` that gates the seconds-format branch before any `Number()` call — only then does the fallback `Date.parse` branch run. **Rule:** when a parser accepts two formats and one is a superset of the other under JS coercion (every parseable integer is also a parseable year), regex-guard the narrow format first; fall through only on regex miss.
- **Surprise (fake timers + the natural microtask boundary make 429-with-Retry-After tests timing-precise):** The two new tests assert that `advanceTimersByTimeAsync(1_500)` shows only the first call and `advanceTimersByTimeAsync(600)` (cumulative 2_100) shows the second. This depends on `sleep(retryAfterMs)` being called *after* the first fetch resolves, which it is — `response.headers.get('Retry-After')` is synchronous. No `await` between the first fetch's `await` resolution and the `sleep(2000)` start, so fake-time control is bit-exact. **Pattern:** when a retry path doesn't cross any awaitable boundaries between "got the failing response" and "started sleeping", `vi.useFakeTimers()` + `advanceTimersByTimeAsync` gives sub-ms test precision. Compare to a hypothetical version that did `await logRetry(response)` between header read and sleep — that would introduce a microtask hop that the timer advance must flush around, adding flakiness.
- **Pattern noted (`MAX_RETRY_AFTER_MS = 60_000` is a circuit-breaker policy, not a courtesy cap):** A 60s cap on `Retry-After` is not "be nice to the user." It's a refusal to let a single upstream config error block an entire `mlFetch` call for an hour. If a server genuinely needs 60+ seconds it should fail the request and let the caller decide — the caller has retry-budget context (batch vs single, user-facing vs background) that `mlFetch` doesn't. **Rule:** any "sleep until upstream-says-N" policy needs a cap that reflects the *caller's* tolerance, not the *server's* request. Capping at request-context timeout (here, 600s for embed; 60s for `/chat`) would also be defensible — chose `60_000` as the more conservative bound that protects all callers including the 600s embed path.
