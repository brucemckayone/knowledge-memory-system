### nmemo-2yv.84 — topology / clustering / drift auto-triggers

- **Lesson:** Module-cached config (`config = loadConfig()` at module init) plus a fire-and-forget HTTP target (here: `http://127.0.0.1:${config.PLATFORM_PORT}/api/...`) creates a hard-to-test seam. A direct `process.env` override at call time has the right runtime semantics but makes prod code think test-mode. A small explicit `_setComputeUrlPortForTesting(port)` seam (underscore-prefixed export, null-or-number override) is the cheapest honest middle: production runs through `config`; tests inject the stub server's bound port without leaking env-var tweaks. Same shape worked for `scheduler.ts`. Worth the four extra lines.
- **Surprise:** The bead's locked Decision specified a `derived_freshness` table with "On fact insert, increment facts_since_compute. When >= threshold, fire compute fire-and-forget." Initial instinct was to put the whole detect-and-fire logic in a single PL/pgSQL trigger. Pulled back — PL/pgSQL has no business calling HTTP endpoints (pg_net / pl/pythonu would be required). The split: DB trigger increments only; platform-layer `maybeFireFactThresholdCompute()` does the atomic compare-and-reset + fires. The atomic reset (UPDATE ... WHERE facts_since_compute >= threshold RETURNING) deduplicates parallel-inserter races without an advisory lock — the second inserter sees `facts_since_compute = 0` and returns 0 rows from RETURNING.
- **Pattern noted:** Time-driven cadences are a real third category alongside DB-reactive and post-event chains. Doc 32 §3 already had the `Scheduled` taxonomy slot; this bead populated it. The single `scheduler.ts` home for all `node-cron` jobs (drift today, `.71` reasoning patrol next, etc.) keeps the lifecycle (`startScheduler`/`stopScheduler` + SIGTERM hook) in one place — every additional time-driven cadence registers there, not in its own ad-hoc setInterval.
- **Pattern noted:** The bead acceptance bullet "Concurrency: all auto-triggered computes go through /api/{topology,clustering,drift}/compute and respect .87's race-window fix" was satisfied for free because every trigger here POSTs to the existing HTTP route. Routing all auto-triggers through the same HTTP endpoints the manual debug paths use means one concurrency story to maintain. This is the same principle as "the freshness gate stays satisfied because both compute kinds fire together" — fewer code paths == fewer concurrency arguments to rebuild.

### nmemo-2yv.63 — merge_entities() FK violation on contradictions (T13 + post-merge integrity)

- **Lesson:** When a later migration adds a FK from a new table back to a long-established parent (here: `contradictions.entity_id → entities(id)` in mig 011) WITHOUT an ON DELETE clause, the parent's merge/delete logic must be updated in the SAME landing. PostgreSQL defaults to NO ACTION; the merge SQL in mig 005 (predating mig 011) had no reason to know about a future FK. Audit pattern: whenever adding a FK to entities, run `git grep "DELETE FROM public.entities"` to check the merge_entities() body needs a re-point step.
- **Surprise:** The bead's recommendation was "re-point rather than CASCADE" — preserving the contradiction trail across merges. But the partial UNIQUE INDEX `idx_contradictions_unique_active` (covering `entity_id` as one of its keys) means a naive `UPDATE contradictions SET entity_id = target_id` can violate the index if both source and target carry an unresolved contradiction with the same (type, fact_a, fact_b, edge_a, edge_b). The dedup DELETE has to mirror the index expression EXACTLY — same COALESCE sentinel UUID and same column tuple. Mis-aligning either would either over-delete or under-delete and fail the merge at the UPDATE.
- **Pattern noted:** PL/pgSQL multi-step migrations like merge_entities() are append-shaped — each "re-point step" gets bolted on. Without a discipline of "every new FK to entities triggers a paired merge-step", these accumulate as latent bugs. Worth filing a future check: a CI lint that verifies every FK with `REFERENCES public.entities` has a corresponding re-point step in merge_entities() or an explicit `ON DELETE CASCADE`/`SET NULL` clause.

### nmemo-2yv.38 — resolveContradiction transactional correctness (concurrency hardening)

- **Lesson:** Threading an optional `tx?: Tx` through mutation primitives (`expireFact`, `invalidateFact`, `expireCausalEdge`, `reviseCausalEdge`) is a clean refactor — the `runUpdate(tx)` helper used either with the passed-in tx or under a freshly-opened `db.transaction(runUpdate)` keeps the existing callers backwards-compatible while letting multi-step orchestrators (here: `resolveContradiction`) own the atomicity boundary. The exported `Tx = Parameters<Parameters<typeof db.transaction>[0]>[0]` type alias in `db/index.ts` is the cheapest way to surface drizzle-orm's transaction type without dragging in pg-core internals.
- **Surprise (caught by /code-review subagent):** Threading tx through the primitives is necessary but not sufficient for full atomicity. `expireFact` and `invalidateFact` delegate to `createCausalEvent` and `cascadeFactExpiry` AFTER their inner tx body returns — those delegations always run on the module-level `db` pool, even when the caller supplied a `tx`. If the outer tx rolls back (e.g. closing UPDATE contradictions throws), the causal_event and cascade-expired edges have already committed on separate connections and stay behind as orphans. This is the next domino — tracked as the bead's "Broader improvement note" follow-up, deferred from .38 by design.
- **Pattern noted:** When extending a primitive with an "optional outer transaction" parameter, the post-mutation side effects (audit emissions, cascade work) usually want the SAME tx-aware treatment. Not threading them is the smaller change but leaves a latent orphan-on-rollback. Whenever this pattern lands again (entity merges, etc.), thread tx ALL the way through or document the partial-atomicity explicitly. The /code-review subagent's "high-confidence" verdict on this gap is correct — the bead's locked scope just chose to defer it.

### nmemo-2yv.37 — edge-mutating contradiction resolution (T13 half-built pipeline)

- **Lesson:** When a polymorphic enum (here: `resolution_type`) dispatches through a TypeScript switch, the `default: const _exhaustive: never` pattern is what catches drift — but ONLY if every layer (DB CHECK, MCP enum, HTTP body cast, agent prompt) is also extended in lockstep. The TS exhaustiveness check protects the dispatcher, not the boundary layers above it. For new vocabulary, edit the union LAST so any layer you missed becomes a compile error against the (already-extended) switch's exhaustiveness verifier. Counter-pattern: don't edit the union first, because then the switch happily accepts unhandled values during the in-progress edits.
- **Surprise:** The bead's "Scoped fix" mentioned six layers (migration, contradictions.ts, causal-agent.ts, index.ts, reasoning_agent.py, doc 16). The seventh (HTTP body inline type union at index.ts:673-676) was visible only as a `body.resolution_type as` cast — not as a type imported from the service layer. This is a pre-existing weak-typing seam that lets the union drift silently; future hardening could replace the cast with `import type { ResolutionType }`.
- **Pattern noted:** The bead listed a "Future direction" footnote about replacing the static enum-dispatcher with a per-contradiction agent call. Option B (this bead) is a stopgap. The TOCTOU race surfaced by the code-review subagent (`expireCausalEdge` is a no-op on already-expired edges → if another path expires the edge between detection and resolution, the contradiction closes with no history row) is a known consequence of the static-dispatch design; the "Future direction" rewrite obviates it.

### nmemo-2yv.60 — resolve_candidate enum / merge_candidates CHECK alignment (T7 naming mismatch)

- **Lesson:** When a CHECK constraint enumerates vocabulary that other layers (tool schemas, agent prompts, table names) also enumerate, a divergence is silent and total — every write of the new value hits the CHECK and fails on the close path, while the upstream side-effect (here: the same_as_links row) lands via a different write path. The bug only surfaces if you check the candidate row's *post-resolution* status rather than the link table. This is a generalisable test-design lesson: when a pipeline writes to two tables and an error in one is recoverable into the other, end-to-end tests must assert *both* terminal states, not just the visible one.
- **Surprise:** The bead's Scoped fix had three steps but the third ("integration test against the DB write path") was the one carrying the regression-guard value. Steps 1 + 2 (migration + grep-for-readers) could have been done blindly with low-confidence safety; step 3 is what locks down the contract. The instinct to land migrations without an exercising test would have allowed a future revert of the CHECK to slip through unnoticed.
- **Pattern noted:** Doc 27 §2.2 already discusses 'same_as' as a training-label vocabulary. The schema CHECK in 003 predates that discussion. Whenever a vocabulary discussion lands in a design doc, run `grep "CHECK.*IN (" platform/src/db/migrations/*.sql` against the new vocabulary to detect drift early. Future work: vocabulary-alignment pass before reasoning_reports (per the bead's "Future direction" note).

### nmemo-2yv.112 — Pi bridge port default 3001 → 3099

- **Lesson:** When a bead's Scoped fix lists multiple edits and one of them is incompatible with the project's actual dev environment, prefer the smallest faithful change that satisfies the bead's *acceptance* over a literal application that introduces a regression. Here the bead asked for `"bridge": "PI_BRIDGE_PORT=3099 tsx src/services/pi-agent-bridge.ts"` in `package.json`, but inline `KEY=value cmd` syntax doesn't work in Windows cmd/PowerShell (the user's primary shell per CLAUDE.md), so `npm run bridge` would have regressed. Skipping that step was the right call because the code-default change at `pi-agent-bridge.ts:38` already satisfies the actual acceptance bullet ("npm run bridge starts the bridge on 3099 with no extra env setup needed"). Always check the bead's *acceptance contract* vs the *implementation list* — the former is the binding spec.
- **Surprise:** Bullet 5 said "deleting ml-services/.env and running make bridge + make ml works (llm.py picks up the 3099 code default)" — but deleting `.env` also strips `LLM_PROVIDER=pi`, which makes `LLM_PROVIDER` default to `claude`, which means `PiBridgeProvider` is never instantiated and the bridge-URL default never gets exercised. The bullet as literally written passes vacuously. To honour the bullet's *intent* (verify the code default), unset `PI_BRIDGE_URL` while keeping `LLM_PROVIDER=pi` and instantiate `PiBridgeProvider` directly.
- **Pattern noted:** Bullet 6 ("Port table in doc 29") referenced a doc owned by a separate bead (`.110`). This is a recurring shape in this review cycle — beads sometimes carry forward dependencies that can't be satisfied at their own implementation time. The skill should treat such bullets as "deferred to the owning bead" rather than halting acceptance.

### nmemo-2yv.31 — 'superseded' fact event_type wired up

- **Lesson:** When a vocabulary value is declared at every layer (TS union, DB CHECK constraint, fixture, doc) but written by ZERO production paths, the gap is invisible to schema-only audits. The fix here was one line in `createFact`'s supersession loop — `eventType: 'superseded'` — but the diagnostic was a grep for production occurrences of the literal. **General rule:** whenever a CHECK constraint enumerates N values, grep production code for each value; any with zero hits is a dead vocabulary slot until proven otherwise.

### nmemo-2yv.83 — drift-reconciliation post-compute trigger (T13 / G4 half-built pipeline)

- **Lesson:** When a bead spec includes example SQL or example payloads, the field names may be from the *consumer's* (payload-side) layer, not the *storage* (column-name) layer. The bead's `## Decision` SELECT used `source_cluster_id` (the agent's `ReconciliationDriftRequest` payload field). The actual column in `entity_drift_events` is `cluster_id_at_detection` (per 016 §3.2). Copy-pasting the bead's SQL verbatim produced a Postgres `column "source_cluster_id" does not exist`. **General rule:** when a bead author writes example SQL, treat field names in the example as conceptual; before writing the query, read the target table's schema and translate. Cheap fix, easy to miss — the test caught it immediately, but a fix landed without a test wouldn't have.
- **Surprise:** The bead's locked spec read "On agent success, the entity_drift_events row has reconciliation_run_id set referencing the agent's generated row in reasoning_reports / gardening_reports / appropriate audit table." Reading the ml-services `/reconciliation-agent/drift` endpoint (`drift.py:771-803`) showed the agent returns ONLY a `{result: str}` — it never writes to reasoning_reports or any audit table. The bead's success-path narrative was aspirational about a future where the agent self-writes audit rows. The faithful minimum-change interpretation: the platform helper writes the audit row itself, capturing the agent's text in `reasoning_reports` with `mode='patrol'` (closest legal CHECK value) and `actions_taken.source='reconciliation_drift_agent'` for disambiguation. A future bead can either add a `'drift_reconciliation'` mode (CHECK relaxation, ~5-line migration) or push the audit-write into the agent itself.
- **Pattern noted:** In fire-and-forget helpers invoked via `void helper()`, any *setup* work (dynamic imports, config resolution) MUST live inside the outer try/catch. A failure above the try escapes as an unhandled promise rejection (Node 20+ default = process death on strict mode). The sibling `triggerCrossClusterAfterCompute` (index.ts:999) already follows this — its dynamic import is inside the try at line 1001. My first cut put the dynamic import on the line above the try; code-review caught it. **Rule:** for any `export async function trigger*(...)` matching the fire-and-forget pattern, the FIRST line of the function body should be `try {` and ALL awaits live inside.
- **Pattern noted (carry-forward, deferred):** Cross-helper concurrency. `triggerCrossClusterAfterCompute` uses `pg_try_advisory_xact_lock(hashtext(LOCK_KEY))` to deduplicate overlapping invocations. The new drift-reconciliation helper does NOT (bead spec didn't require it). Two overlapping `/api/drift/compute` calls would double-invoke the LLM and orphan one of two `reasoning_reports` rows per drift event. Bead `.88` is the natural home for sweeping both helpers into a services module — at that point, also adopt the advisory lock pattern uniformly. Tracked in the bead's deferred-follow-ups note for whoever picks up `.88`.

### nmemo-2yv.87 — compute endpoints: pg_try_advisory_xact_lock replaces SELECT-then-INSERT pre-check

- **Lesson:** When replacing a SELECT-then-INSERT race-prone pattern with a transaction-scoped advisory lock, the WHOLE compute work has to live inside the same transaction — otherwise the lock releases the moment any intermediate `conn.commit()` fires. This forces a structural shift: the old pattern committed the `in_progress` row early so external observers could see the work in flight; the new pattern only commits the `completed` row at the very end, and failures roll back the entire transaction (no `failed` row persists). Module-level docstrings that described the old "marked 'failed' on rollback" behaviour become stale and need updating in the same diff. The status table changes meaning: from "in-flight + final outcomes" to "completed runs only". Anyone relying on early in-progress visibility (status endpoints, dashboards) must instead query `pg_locks`.
- **Surprise:** Both the bead spec's example SQL AND my first cut wrote the `except Exception as exc:` block, refactored to `except Exception:` (no binding), and left a stray `raise HTTPException(..., detail=f"...{exc}")` referencing the now-undefined `exc`. The dead-line wasn't reachable (preceding unconditional raise), so no linter-free runtime would surface it — but the code-review subagent caught it as F821 undefined-name in a hypothetical-future scenario where someone removes the preceding raise. **Pattern:** whenever an `except As name:` clause loses its `as name`, immediately scan the rest of the except body for surviving references to `name`. Editor multi-cursor or grep-and-replace is the safer path.
- **Pattern noted:** Postgres `pg_try_advisory_xact_lock(<integer>)` has ONE namespace across all single-argument callers — int4 widens to bigint via implicit cast. Writing "different namespace" in a comment because one caller uses `hashtext('text')` (int4) and another uses literal bigints is technically wrong; only the *values* differ, not the namespaces. The locks.py module now documents this explicitly with the int4 range upper-bound guarantee for the hashtext-derived caller vs the small bigints 1001-1003. Future bigint callers MUST stay outside int4 range or compute the hashtext literal to prove non-collision.
- **Pattern noted (carry-forward):** Three nearly-identical handler bodies (topology / clustering / drift) all wrap the same lock-acquire pattern with only the lock key constant differing. Extraction to a helper (e.g. `with acquire_compute_lock(conn, 'topology'):`) is tempting but premature — the bead's locked spec didn't call for it, and the inline shape keeps the lock-key-to-endpoint mapping explicit at every site. If a fourth caller lands in this style, extract then.

### nmemo-2yv.53 — update_entity_summary write-side T8 hardening (length cap + sanitize)

- **Lesson:** When a parent helper bead (.62) has already shipped a sanitiser AND wrapped every read-back boundary, the dependant write-side bead is reduced to one decision: hard-reject vs soft-truncate on the write path. The bead's NOTES (REVIEW-7 COORDINATION) hinted at this, but the Scoped-fix section was not updated to match — read both, treat NOTES as authoritative when they conflict with Scoped fix.

- **Pattern noted:** Normalisation tests are easier to debug if the expected output is derived from the algorithm, not pre-written. My first cut wrote `line one\nline two\nline three` as the expected substring; the actual output had `\n\n` between `two` and `three` because the C0 strip removes `\x01` cleanly but leaves the surrounding newline run, which then collapses to 2. ### nmemo-2yv.29 — createFact dedup branch wrapped in db.transaction for audit atomicity

- **Lesson:** When a mutation primitive already has a tx-aware sibling pattern (here: four other paths in `facts.ts` already wrap UPDATE + recordFactChange in `db.transaction(async (tx) => {...})` and thread `tx`), the cheapest test for "is this branch broken?" is to ask whether it follows the sibling shape. The dedup-and-corroborate branch was the odd one out. The fix is mechanical once the pattern is established; the discovery is what costs. **General rule:** when reviewing service-layer mutations for atomicity gaps, list every mutation path in the file and check whether each one wraps its audit emission. The non-wrapped one is the bug.
- **Pattern noted:** The bead's locked spec spelled out the exact code shape (`await db.transaction(async (tx) => { ... await recordFactChange({ ..., tx }); });`) — and the implementation took 2 lines + a comment. The locked spec being concrete made this a fast bead; vague specs would have invited drift. Worth noting that beads where the Decision section includes a *code snippet* are the cheapest to drive.
- **Pattern noted:** The CHECK-violation test pattern (`actor: 'no_such_actor' as any` flowing through to a raw-SQL INSERT that hits the CHECK constraint at runtime) is a clean way to force a downstream-only failure mode. TypeScript erasure means the runtime sees a string the DB rejects, exercising the rollback path without contriving a network blip or DB mock. Reusable for any other tx-wrapped audit row that has a CHECK constraint downstream.

### nmemo-2yv.61 — reconciliation agent pipeline auto-trigger (T12 design-contract drift)

- **Lesson:** When a "documented contract" (here: the reconciliation_agent.py system prompt's "You run AFTER extraction" assertion + RECONCILIATION_AGENT_REVIEW.md's "fire-and-forget at pipeline.ts line 188" description) quietly falls out of the code over a release cycle, the doc becomes a liar but the system keeps shipping. Audit pattern: grep the doc's claimed call sites against the current code at every doc touch, and fail loudly when the line/symbol referenced no longer exists. The bead-finding process caught it here; a CI lint that diff-checks docs vs code references would have caught it earlier.

Initial implementation copied the handler's narrower gate. Re-reading the bead spec caught the deviation. **Pattern:** when the bead spec and the existing manual code path disagree on a parameter (here: status enum scope), the bead's locked spec wins by definition — but always re-read the spec after looking at the existing code, since the existing code biases the implementation.
- **Pattern noted:** Wall-clock cooldown gating via a module-level timestamp is simpler than counter-based cadence (the gardener's pattern) when the rate-limit metric is "minimum N minutes between calls" rather than "every N events". ### nmemo-2yv.124 — Delete causal-mcp.ts + dead CAUSAL_AGENT_TOOLS export

- **Lesson:** Pure-deletion beads (drop a dead file + stale exports + outdated comments referencing them) compress the full /code-review + /simplify pipeline into a single grep-pass: if every reference to the deleted symbols is gone from production source, the code-review verdict is "clean by construction" and /simplify has nothing to simplify. Pattern: when a bead is a clean delete, the acceptance bullets typically encode the review (zero-hit grep checks across the codebase) and there is no test surface to add. Don't over-process — three Edits and a grep give the same coverage as a 5-angle review.
- **Pattern noted:** A `/** @deprecated */ export const X = []` empty-array placeholder is worse than no export. If anything later imports `X` (refactor, search-and-replace), the consumer runs with an empty tool array and the agent silently misbehaves. The right shape for a deprecated symbol is *removal*, not *zero-out + deprecate*. Apply this lesson the next time we deprecate an exported collection: delete, don't empty.

### nmemo-2yv.101 — patternImpact.nodeType honesty fix (lying cast → honest union extension)

- **Lesson:** When a value gets force-cast through a TS type with an inline `// smell comment` apologising for it (here: `nodeType: 'fact' as ImpactNodeType, // patterns aren't a graph node type — represented as fact-class for the report`), the cleanest fix is almost always to extend the type to admit the honest value, not to find clever ways to suppress the cast. Two-line type union extension + cast removal + matching test + doc — the whole bead is mechanical. The smell comment IS the to-do flag pointing to the right fix.
- **Pattern noted:** Acceptance bullets that ask for a "no `as X` cast, no smell comment" check are a high-signal acceptance shape — they're auditable by grep alone, and they encode an invariant that survives future refactors. Worth replicating: when removing a lying cast, the acceptance bullet should explicitly forbid both the cast AND the apology comment so neither can sneak back in.

### nmemo-2yv.111 — Compose platform /health with Qdrant + ml-services (G1 health composition)

### nmemo-2yv.30 — Replace PL/pgSQL merge_entities() with audited TS mergeEntities()

- **Lesson (UPDATE...RETURNING for audit-set integrity):** When a single TS function must (a) mutate a set of rows and (b) emit one audit row per mutated row, the SELECT-then-UPDATE pattern is a race seed under READ COMMITTED isolation. Between the SELECT-of-affected-ids and the UPDATE-of-same-where, a concurrent inserter can land a NEW row matching the WHERE; the UPDATE then mutates it without producing an audit row, leaving audit-set drift from mutation-set — the exact silent gap the original PL/pgSQL function had. `UPDATE ... RETURNING id` collapses both into one atomic statement; the RETURNING set is provably the mutation set. Apply this anywhere the bead's acceptance bullet specifies "every affected row gets exactly one history row" — the only way to keep that as a HARD invariant (vs best-effort) is the single-statement form. Generalises: whenever a future bead adds another "audit every mutation" service primitive, default to UPDATE...RETURNING / DELETE...RETURNING; avoid SELECT-then-mutate splits.
- **Lesson (FactEventType extension contract):** Adding a new event_type value requires lockstep edits across two layers — the TS union in `src/services/audit.ts:FactEventType` AND the DB CHECK constraint in `fact_history.valid_fact_event_type`. The migration that ALTERs the CHECK carries a comment naming the TS file (same SSOT discipline as bead .130 RESOLUTION_VALUES). The Actor union is similarly co-located (mig 009 line 47-50 + audit.ts line 69-76). Pattern noted: any future audit lifecycle event should follow the same shape — extend the union LAST so any layer missing the matching DB constraint fails CI at the test-write level. The CHECK constraint test scenarios (it.each + parameterised) used by .130 for RESOLUTION_VALUES would also catch a missed `event_type` value addition.
- **Lesson (port semantics, not just SQL):** When porting a PL/pgSQL function to TS, the temptation is to translate one-to-one. But the audit invariant is the actual contract — the SQL function had a "best effort" audit because it had no audit calls at all; the TS port must be exact. Doc 12's Phase 1 audit-trail contract says "every mutation to a fact MUST write exactly one audit row". The bead's locked Scoped fix correctly defined "one history row per affected fact" — translating verbatim with SELECT-then-UPDATE would have shipped the gap; the /code-review pass that surfaced the race window earned its keep here. Don't trust "this is the same code in a different language" — re-derive the contract from the acceptance bullets.
- **Lesson (postgres.js + drizzle dual usage):** `tx.execute(sql\`...\`)` is drizzle, RETURNS the postgres.js native row shape (snake_case keys). The `unwrapRows<T>()` helper from audit.ts is the right normaliser — it handles both `Array<T>` (postgres.js direct) and `{ rows: T[] }` (some adapter paths) shapes in one cast. Generalises: in any service-layer code that mixes drizzle's `sql\`...\`` tagged templates with raw row access, route returns through `unwrapRows<{ snake_case_columns: type }>(...)`. The drizzle-orm `.select()` builder is a different beast — that path returns camelCase mapped per the schema; only the raw-SQL path needs `unwrapRows`.
- **Surprise (NOW() inside a transaction = constant timestamp):** Two `recordFactChange` calls inside the same tx for the same fact (e.g. a duplicate fact that gets BOTH subject-re-pointed AND duplicate-expired in the same merge) produce fact_history rows with IDENTICAL `occurred_at` — `NOW()` returns transaction-start time, not statement-start time. Test assertions ordering rows by `occurred_at DESC` cannot rely on insertion order within a single tx. Use set-membership assertions (`reasonings.some(r => r.includes('subject re-pointed'))` and `reasonings.some(r => r.includes('duplicate fact expired'))`) instead of positional access. Generalises: any test that asserts the order of audit rows produced inside a single tx should use a set / array-contains pattern, not `rows[0]`/`rows[1]`. - **Surprise (drizzle sql + JS array → uuid[] coerces poorly):** The pattern `WHERE id = ANY(${jsArray}::uuid[])` inside a drizzle `sql\`...\`` template fails at runtime with `malformed array literal: "<uuid-string>"` because drizzle treats `${jsArray}` as a SCALAR parameter, sends the first array element as `text`, then postgres tries to cast that text to `uuid[]` and falls over. The portable substitute is `(VALUES (${id1}::uuid), (${id2}::uuid), …)` joined via `sql.join(arr.map(x => sql\`(${x}::uuid)\`), sql\`, \`)` — already memorialised in `bd memories` from bead .42 (`drizzle-sql-template-doesn-t-reliably-serialise-js`). The lesson here: even when you know the pitfall, the first instinct is still to write `ANY(arr::uuid[])` and discover it again at test time. UPDATE...RETURNING avoided this entirely for steps 4-6 because the mutation IS the affected-id selector — no separate array-of-ids parameter needed.
- **Pattern noted (single-statement mutation = simpler shape):** The refactor from SELECT-then-UPDATE-then-for-loop to UPDATE...RETURNING-then-for-loop removed the intermediate `duplicateIds` JS array AND removed the need for the VALUES-list shim — the refactor SHRANK the diff while strengthening the contract. When two patterns are equivalent on the happy path but one has a smaller surface area for races AND fewer JS-to-SQL serialisation steps, the smaller-surface one wins on both correctness and simplicity. The lesson generalises beyond audit: ANY "mutate then collect ids" pair should be UPDATE...RETURNING.

Replacing `SELECT public.merge_entities(...)` with `await mergeEntities({...})` preserved that integration point unchanged — the caller still receives `{ survivorId }`, still has the same surrounding try/catch, still kicks off the post-merge compute hook on success. Cross-bead contract preservation costs nothing when the public surface (call shape + return shape + error surface) is held constant. Worth replicating: when refactoring an interior call site, return SHAPE compatibility is cheaper than caller-side adapter code.

### nmemo-2yv.65 — merge_entities() dangling-UUID re-point (topology_bridges FK + reasoning_reports.entity_ids[] array)

- **Lesson (a missing FK on a derived-data table is BOTH a runtime bug AND a recompute-cost decision):** `topology_bridges` had UUID NOT NULL columns with no `REFERENCES` clause since mig 014 — bridges from any merged source entity persisted as dangling rows. The fix has two halves and they're separable: (i) add the FK so future drift can't accumulate, (ii) re-point in the merge transaction so the survivor inherits the bridge. ON DELETE CASCADE is the right semantic specifically because bridges are derived data (igraph.bridges() output) — a CASCADE-dropped bridge regenerates on the next gardener pass. For non-derived FK targets, the same shape would need `ON DELETE NO ACTION` + an explicit re-point step instead. **Audit pattern:** when adding a FK to `entities`, classify the holding table as derived-recomputed (CASCADE) or canonical (re-point + NO ACTION). The mig 028 vs mig 020 (contradictions) split is the canonical example.
- **Lesson (canonical-order CHECK + UNIQUE constraint forces a 4-statement re-point shape):** topology_bridges has BOTH `CHECK (source_entity_id < target_entity_id)` AND `UNIQUE (source_entity_id, target_entity_id)`. A simple `UPDATE source_entity_id = target` cannot satisfy both unconditionally — order-preserving re-points need their own UPDATE; order-violating cases must be dropped (CASCADE handles them after source DELETE); unique-clash duplicates must be DELETED before the UPDATE; self-bridges must be DELETED after the UPDATE. Four statements total: pre-delete-unique-clash → update-low-side → update-high-side → post-delete-self-bridges. Pattern mirrors same_as_links step 11 (mig 005:138-145) but adds the unique-clash pre-pass that same_as_links omits (and that .64 will need to fix for same_as_links). The order matters: pre-delete-unique-clash must come BEFORE the updates (otherwise the UPDATE violates UNIQUE); post-delete-self-bridges must come AFTER (a row where target_entity_id == sourceId AND source_entity_id == targetId is created by the high-side UPDATE on a pre-existing (targetId, sourceId) row only if both endpoints are involved — practically, the row exists pre-merge as (lower, higher) where {lower, higher} == {source, target}, and the canonical-order check on the UPDATE branches both skip it, leaving it for the post-DELETE step).
- **Lesson (array_replace for FK-impossible columns is the canonical idiom):** `reasoning_reports.entity_ids UUID[]` cannot carry an element-level FK in Postgres — array columns don't compose with REFERENCES. The merge transaction must imperatively `UPDATE ... SET entity_ids = array_replace(entity_ids, ${sourceId}::uuid, ${targetId}::uuid) WHERE ${sourceId}::uuid = ANY(entity_ids)`. The WHERE clause limits the scan via the existing GIN index; the SET re-indexes on UPDATE. No audit emission needed — `reasoning_reports` is a provenance log of agent passes, not a mutating-fact-state assertion. **Audit pattern:** grep `UUID[]` and `UUID NOT NULL DEFAULT '{}'` migrations for other array-of-entity-id columns that need the same `array_replace` treatment — `reasoning_reports.fact_ids` and `causal_edge_ids` are sibling columns in the same table (out of scope for .65 since they reference facts and edges, not entities).
- **Surprise (the bead body called for the CASCADE FK; the design discussion calls for re-point):** The bead's Scoped fix says step 1 = add `REFERENCES public.entities(id) ON DELETE CASCADE` AND step 2 = imperatively re-point in `merge_entities()`. The two steps appear redundant — wouldn't CASCADE alone clean up the dangling rows? It would. The reason to ALSO re-point is preservation: a CASCADE-only solution drops the bridge entirely; a re-point preserves the bridge against the survivor entity. For derived data (regenerates on next gardener pass) the cost is low, but the re-point shortens the window of "broken bridge data" from one-gardener-pass to zero. **Implication:** when a fix has a "make-the-bug-impossible" half (FK) AND a "preserve-information" half (re-point), the two are complementary, not alternatives. CASCADE catches the cases the re-point misses (canonical-order violations) and prevents future regressions; re-point preserves what can be preserved on the happy path.
- **Pattern noted (test must control UUID ordering for canonical-order-sensitive assertions):** The canonical-order CHECK means a re-point assertion's success depends on the random UUID ordering of the test entities — if `peer.id < target.id`, `(source, peer)` re-points to `(target, peer)` (canonical) and survives; if `peer.id > target.id`, `(source, peer)` re-points to `(target, peer)` which violates `target_entity_id < target.id`, so the UPDATE branch skips it, and CASCADE drops it. The fix: generate 5 candidates via `Promise.all`, sort by id, assign roles by rank (`peerLow < target < source < peer1 < peer2`). Every re-point branch then lands in its intended outcome deterministically. **Generalises:** any test asserting "this row survives the re-point with shape X" against a canonical-order table must pin entity-id ordering. ### nmemo-2yv.119 — ml-client 429 + Retry-After

- **Lesson (rate-limit responses need a different sleep schedule than transient-infra responses):** The pre-bead `RETRY_STATUS_CODES = {502, 503, 504}` set lumped all retryable errors into one linear `[500, 1000]ms` backoff. 429 is semantically different — it's a *cooperative* signal from a healthy server that says "the schedule is yours to read in `Retry-After`." Retrying at 500ms when the server said `Retry-After: 5` either re-throttles (best case) or earns the caller a per-IP ban (worst case). The fix shape is one status-code-conditional branch in the retry path: only 429 consults the header; 502/503/504 keep the linear schedule. The branching is narrow enough that it doesn't justify a per-status-code dispatch table — `response.status === 429` is the only special case until a real second one appears. **Rule:** when a retry set spans semantically different error classes (transient infra vs cooperative rate-limit vs auth-rotation vs ...), the sleep policy should fork on the class, not be unified.
- **Lesson (regex-then-fallback parser shape beats `Number()`-then-`Date.parse()`):** `Retry-After` accepts two formats — a non-negative integer-seconds count OR an HTTP-date string. The naive shape `const n = Number(h); if (Number.isFinite(n)) ... else Date.parse(h)` is wrong because `Number("Wed, 21 Oct 2026 GMT")` is `NaN` (fine) but `Number("2026")` is `2026` (also fine — and `Number.isFinite(2026)` is `true`), and the function would interpret a date-year string as 2026 *seconds*. The cure is a regex guard `^\d+(?:\.\d+)?$` that gates the seconds-format branch before any `Number()` call — only then does the fallback `Date.parse` branch run. **Rule:** when a parser accepts two formats and one is a superset of the other under JS coercion (every parseable integer is also a parseable year), regex-guard the narrow format first; fall through only on regex miss.
- **Surprise (fake timers + the natural microtask boundary make 429-with-Retry-After tests timing-precise):** The two new tests assert that `advanceTimersByTimeAsync(1_500)` shows only the first call and `advanceTimersByTimeAsync(600)` (cumulative 2_100) shows the second. This depends on `sleep(retryAfterMs)` being called *after* the first fetch resolves, which it is — `response.headers.get('Retry-After')` is synchronous. No `await` between the first fetch's `await` resolution and the `sleep(2000)` start, so fake-time control is bit-exact. **Pattern:** when a retry path doesn't cross any awaitable boundaries between "got the failing response" and "started sleeping", `vi.useFakeTimers()` + `advanceTimersByTimeAsync` gives sub-ms test precision. Compare to a hypothetical version that did `await logRetry(response)` between header read and sleep — that would introduce a microtask hop that the timer advance must flush around, adding flakiness.
- **Pattern noted (`MAX_RETRY_AFTER_MS = 60_000` is a circuit-breaker policy, not a courtesy cap):** A 60s cap on `Retry-After` is not "be nice to the user." It's a refusal to let a single upstream config error block an entire `mlFetch` call for an hour. If a server genuinely needs 60+ seconds it should fail the request and let the caller decide — the caller has retry-budget context (batch vs single, user-facing vs background) that `mlFetch` doesn't. **Rule:** any "sleep until upstream-says-N" policy needs a cap that reflects the *caller's* tolerance, not the *server's* request. Capping at request-context timeout (here, 600s for embed; 60s for `/chat`) would also be defensible — chose `60_000` as the more conservative bound that protects all callers including the 600s embed path.

The Pi bridge had no such surface: `/run` requires an LLM session to drive tool dispatch, which would make the parity assertion depend on model availability + credentials + flaky generation. Adding a tiny `POST /tools/call` debug endpoint that mirrors the MCP envelope shape (`{ content: [{type, text}] }` on success, `{ isError, content: [...] }` on throw) gives both transports a model-free invocation path that proves the contract directly. **Rule:** when filing a parity test across two transports, the cheapest first step is to give each transport a *debug* dispatch endpoint with identical envelope semantics. Production paths can stay as they are; the test endpoint just needs to land in the same envelope so the assertions on the two outputs become symmetric.
- **Lesson (parity tests need shared DB visibility — bridge processes inherit DATABASE_URL from their startup env, not the test's runtime env):** Case 3 (write-serialization) creates entities via `testDb` (`cognitive_test` on 5433) and then issues `create_fact` over HTTP to the Pi bridge. The bridge process was started with the default `.env` (`cognitive` DB) and saw none of the test entities — FK violation. Fix: restart the bridge with `DATABASE_URL=postgres://...cognitive_test` set explicitly. `npm run bridge` reads `.env` at boot; per-invocation env passes through. **Rule:** any test that drives a long-running server process and expects DB writes to be visible to both sides must either (a) point the server at the test DB at startup or (b) use a transport endpoint that loops back into `handleToolCall` in-process (the latter only works for the MCP-server path, not the Pi bridge HTTP path). Document the bridge-restart requirement in the test's docstring so the next runner doesn't trip on it.
- **Surprise (the bridge process's tool count was 42, not 38 as recent beads mentioned):** Bead `.128`'s description quoted "currently 38 tools." Live count via `GET /tools` returned 42. `GRAPH_TOOLS` grew under intervening landings; the parity test correctly references `GRAPH_TOOLS.length` rather than hard-coding a number, so this drift didn't break anything — but it confirms doc 30's "this doc does not hard-code a number" guidance. **Rule:** tool-count assertions must always reference `GRAPH_TOOLS.length`, never a literal. Doc references to tool count must use "currently N" with the date of writing — never `expect(...).toBe(N)` against a literal.
- **Pattern noted (parity-as-symmetry-not-duplication):** The new Pi `/tools/call` endpoint mirrors the MCP server's `tools/call` wrapper (`graph-mcp.ts:45-58`) — same try/catch, same envelope, same error-text prefix. A simplify pass might call this "duplication" but it's *the contract being tested* — both transports MUST produce the same envelope for the same input, and the only way to enforce that is to land both wrapper implementations next to each other and assert their outputs match. **Rule:** when implementing a parity contract, intentional symmetry between two implementations is the test surface; do not extract to a shared helper unless both implementations would naturally share the helper without the parity test pressuring them to (i.e. the helper is justified independently). The MCP server is an external SDK; the Pi bridge is local HTTP — no natural shared helper, so the symmetry stays inline.

### nmemo-2yv.105 — Observability log line for `analyzeImpact` invocations

- **Lesson (a service-level `actor` parameter buys log partitioning at near-zero cost):** Bead F4 (`.102`) had already established the actor-threading contract for `maybeWarnBlastRadius`; F7 extends the same idea one layer deeper — into `analyzeImpact` itself, where the parameter defaults to `'unknown'` to keep the contract minimal-change. Three call sites land different literals (`'http'`, `context.agent`, `'preflight'`), which gives the operator a one-token grep distinction (`grep '[impact] actor=preflight'` separates destructive-path observability from direct HTTP/MCP reads) without threading actor through every internal caller. **Rule:** when a function gets observability instrumentation, add an `actor?: string` parameter on its public params interface with a sane default; populate it from each known dispatch site with a stable literal. The default + caller-known-literal pattern keeps the diff small while making the log stream queryable by source.
- **Lesson (`try/catch` at the orchestrator boundary, re-throw to preserve upstream contracts):** The bead's error-path spec required wrapping the orchestrator body to emit a `[impact] error` line, then re-throwing so the HTTP endpoint's existing 404/500 mapping (`/not found/i` → 404, else → 500) keeps working unchanged. The `try` block needs to wrap `loadRootNode`'s throw too — putting `startMs = Date.now()` outside the `try` and the throw-detection inside is what the bead implicitly requires (the bead's "wrap the orchestrator body in try/catch" is the smallest scope that catches every internal throw). **Rule:** when adding error-path observability to a function with downstream try/catch consumers, the only safe shape is `try { ...body, log success... } catch { log error; throw }` — never `try { ... } catch { log; return null }` because the upstream contract treats `throw` as a typed signal (404 vs 500).
- **Lesson (spy tests for log lines stabilise contract via `mockRestore` + `try/finally`):** `vi.spyOn(console, 'info').mockImplementation(() => {})` swallows the log line so the test doesn't pollute the report; the assertion reads `spy.mock.calls` and finds the line by `startsWith('[impact] ')`. Critically, the test wraps the assertions in `try { ... } finally { spy.mockRestore() }` — without `mockRestore`, a failing assertion would leak the spy into the next test in the file and confuse the report. **Rule:** every `vi.spyOn(console, ...)` test pairs with `mockRestore()` in a `finally` block. The cost is two lines; the bug it prevents (silent test-cross-contamination) costs hours.
- **Pattern noted (the bead's "Optional" tests are worth landing when their cost is trivial):** The bead listed the spy-based tests as optional ("If the implementer wants belt-and-braces..."). Two spy tests (success + error) land in ~30 LoC and cost <100ms to run. They flip red the moment the log line shape drifts — which is the exact kind of contract the bead is creating. Skipping them would leave the contract documented in code-comments only. **Rule:** the bead's "optional" classification is a minimum-bar, not a recommendation; land optional tests when their cost-to-implement is dominated by the cost-of-skipping (here: the contract has no other guard).
- **Pattern noted (preflight gets its own actor literal, not `context.agent`, because the .102 warn line already covers caller attribution):** Three preflight call sites in `causal-agent.ts` know `context.agent` and pass it to `maybeWarnBlastRadius`. The bead's "Out of scope" guidance said don't thread actor through every caller. Resolved by giving `preflightBlastRadius` itself an internal literal `'preflight'` — every preflight invocation logs the same actor regardless of which agent triggered the destructive path, because the agent attribution is already captured on the `[blast-radius]` warn line from `.102`. The `[impact]` line's actor field then carries the *invocation purpose* (preflight vs read), and `[blast-radius]` carries the *agent identity*. The two log streams compose, not duplicate. **Rule:** when two observability features touch the same code path, give them orthogonal axes — `[impact] actor=...` carries purpose, `[blast-radius] actor=...` carries identity. Both can fire on the same call without redundant data.

### nmemo-2yv.106 — Rule 1b tiered: low-corroboration sole-evidence loss is `high`, not `critical`

- **Lesson (severity ladders need a "trust loss" axis, not just a "cascade fires" axis):** The original Rule 1b conflated two distinct signals — *will the edge be removed by the cascade?* (yes for all sole-evidence citations under hypothetical=expire) and *how trustworthy was that edge?* (corroboration_count). Collapsing both into `critical` made `severitySummary.critical` un-actionable: an agent could no longer distinguish "the cascade will wipe out a 5-source-corroborated edge" from "the cascade will wipe out a 1-source weakly-cited edge." Splitting Rule 1 (corr ≥ 3 → critical) from Rule 1b (corr < 3 → high) restores the signal-quality distinction the spec encoded in the `>= 3` floor. **Rule:** when a severity rule collapses two orthogonal signals into one tier, the resulting counts lose their query value. Either split the rule into tiers OR pick the signal that maps better to operator decisions and let the other fall through. Never broaden silently and never gate behind a code comment that says "we extend the spec to all X cases" — if the broadening was right, update the spec doc in the same diff.
- **Surprise (bead line refs drift across sibling beads in the same area):** The bead said Rule 1b lived at `impact.ts:697-703`; the actual current location was `:850-856`. Cause: bead `.105` (structured log line, same `scoreSeverity` neighbourhood) inflated the file ~150 lines after `.106` was written. `Grep` on the literal rule pattern (`Rule 1b`, `corroboration floor`) found it instantly. **Rule:** treat bead line refs as conceptual pointers, never literal. Re-grep on rule names, comment markers, or unique substrings before assuming the bead is talking about a different code site. Same lesson as `.123` (`## Result` snapshots age) and `.31` (test files added by later beads couple to current behaviour).
- **Pattern noted (fixture-driven tests inherit a fixture's design choices — re-check assumptions when a tier flips):** The `fan-out-explosion.sql` fixture seeds 500 edges with `corroboration_count = 1, strength = 0.7`. Under the old Rule 1b every edge scored `critical`; under the new tier every edge scores `high` (low-corroboration sole-evidence). The fixture didn't need editing — its purpose is performance + zero-mutation, not severity-counting — but the *test assertion* against the fixture did. **Rule:** when a severity-rule tier changes, every test that filters fixture output by severity needs an audit. Search `severity === '<old-tier>'` and `severity === '<new-tier>'` across the test files touched, not just the one named in the bead spec.
- **Pattern noted (doc + code + tests must move in the same commit when a tier splits):** Doc 15's severity table is the spec; Rule 1b is the implementation; the tests are the contract. Landing any two without the third leaves the system in a state where the next reader can argue either way about which is right. The bead's Decision section pre-specified all three updates — easy to land them in one diff. **Rule:** for any severity / vocabulary / enum change, the design doc table, the implementation switch, and the test assertions land in the same commit. Splitting them across commits invites drift between landing and review.
