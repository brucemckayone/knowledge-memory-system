## 1. nmemo-umf — causal delta-scoping and the measured thinness

**Verdict: PARTIAL.** Severity **high** (it blocks any credible evaluation of Graph C, which is the
bead's own sequencing point). Fix size **needs-design**, with two **one-line** sub-fixes that are
independently worth doing (see §1.5).

### 1.1 What the bead gets right [V]

Delta-scoping exists exactly as described.

- `platform/src/services/causal-pass.ts:110` — the pass returns immediately unless *this* promotion
  minted causal events. It is only ever reachable per-epoch.
- `causal-pass.ts:115-118` — `newEvents` = the events named in `promotion.mintedCausalEventIds`.
- `causal-pass.ts:121-123` — touched entities = subjects of those minted events, `.slice(0, CAUSAL_PASS_SCOPE_CAP)`.
- `causal-pass.ts:156-167` — the whole scope is capped at `config.CAUSAL_PASS_SCOPE_CAP`, default **200**
  (`platform/src/config.ts:127`), with a `console.warn` on truncation. Not silent, as the bead says.
- `platform/src/pipeline.ts:1104` — the only caller. [V]

### 1.2 What the bead gets wrong [V]

**"NEVER in the same scope" is false.** Two escape routes exist and one of them demonstrably works.

1. **The neighbourhood has no time window.** `getEntityCausalHistory` (`causal.ts:1085-1124`) selects
   *every* event whose `subject_entity_id` is the touched entity, with no date or epoch predicate, plus
   every active edge touching them. So a cause ingested in batch 1 **is** in batch 5's scope whenever
   batch 5 touches that entity — or touches any entity that was a subject in batch 1's neighbourhood.
2. **`propose_causal_edge` performs no scope-membership check.** `causal-agent.ts:3502-3576` validates
   only that the epoch context exists, that reasoning is non-empty, and that there is at least one
   source ref. It reports `refsResolve` as a *soft* signal. The causal agent also holds the **entire
   read-only tool surface** (`CAUSAL_SURFACE`, `causal-agent.ts:1618-1621`) including
   `get_causal_history`, `trace_causes`, `search_similar_entities` and `find_causal_ghosts`, and its
   prompt says so explicitly: "The scope is the start, not the limit"
   (`ml-services/app/causal_agent.py:58`).

So the correct framing is **effective**, not **structural**, invisibility.

### 1.3 The data: cross-batch edges exist, and every one uses the neighbourhood bridge [V]

`causal_events` has no `epoch_id`, so I used **`date_trunc('second', created_at)`** as the batch proxy.
Proxy validated: 35 epochs appear in `staging_causal_edges`; of the 33 with resolvable refs, **25 touch
exactly one second-cluster**, 5 touch two, 2 touch three, 1 touches four — and the multi-cluster ones
are precisely the epochs that reached prior-batch events. 93 distinct second-clusters vs 35 causal-pass
epochs vs about 30 clusters on 2026-08-31 alone; the granularities line up.

Edge classification (active edges, n=1043):

| class | edges |
|---|---|
| both endpoints minted in the same batch | **1027** (98.5%) |
| cross-batch, cause earlier | **15** |
| cross-batch, cause later | 1 |
| max cause-to-effect creation gap | 24.9 days |

Now the mechanism test. Define the **co-scoped** class: pairs (a in an earlier batch, b in a later
batch) where `a.subject_entity_id` is also a subject of some event in b's batch — i.e. exactly the set
the entity-neighbourhood bridge can surface.

| forward pair class | available ordered pairs | edges formed | rate |
|---|---|---|---|
| within-batch (unordered) | 1,798,866 | 1,027 | 5.71e-4 |
| cross-batch, **co-scoped** | 369,142 | **15** | 4.06e-5 |
| cross-batch, **not co-scoped** | ~157,080,773 | **0** | 0 (Poisson 95% upper about 1.9e-8) |

And at the **proposal** level, before any disposal — 1,251 staged rows, 1,086 with both event ids
resolvable: **1,069 within-batch, 17 cross-batch, and 0 non-co-scoped.** Over 35 epochs the agent never
once used its read tools to propose an edge outside its pushed scope, despite being told it could.

(Side finding [V]: **165 of 1,251 staged proposals — 13.2% — cite event ids that do not exist**. One of
the dangling ids in §4, `68e29fa5-9a59-d39a-9eac-73836ecf9c57`, is not even a valid v4 UUID. Disposal
drops them correctly, so this is a cost and quality signal, not a correctness bug.)

### 1.4 Can I establish *causation*? No. [V] on the numbers, explicit **[I]** on the limit

Doc 44's numbers all reproduce exactly on the live substrate: **1-hop 1043 / 2-hop 142 / 3-hop 12 /
4-hop 3**; **125** of 17,847 events have both in- and out-degree; 1,790 events have any degree; 747
connected components with the largest at **7** event nodes (9 components of 6, 11 of 5, 38 of 4, 146 of
3, 542 of 2).

What the evidence supports: **the reachability boundary of delta-scoping coincides exactly with the
observed edge support.** Not one edge, and not one proposal, lies outside
`same-batch union neighbourhood-bridged`. Delta-scoping is therefore a **binding constraint** — a
necessary condition on the shape of the graph.

What the evidence does **not** support: that delta-scoping **caused** the thinness. The confound is
structural and I cannot design it away from observational data: the co-scope class is *defined* by
entity co-occurrence, and entity co-occurrence is also the best available proxy for genuine causal
relatedness. A world in which real causality only ever holds between events about the same or
jointly-touched entities produces the identical zero. There is no independent oracle for "true
cross-batch causal link" on this corpus, so the 0/157M cannot be read as 157M misses.

The honest statement for the bead: *delta-scoping bounds what Graph C can ever contain, and the bound is
saturated — but the fraction of that bound that represents lost real causality is unmeasured, and
measuring it needs a labelled cross-document causal set, not more SQL.*

One further reason to distrust the bead's stated mechanism as *the* cause: the graph is 86% one-hop even
**within** single batches, where scoping is not a constraint at all. 1,027 of 1,043 edges were formed
inside one scope, and they still produced only 142 two-hop paths and a largest component of 7. **[I]**
Whatever limits chain formation appears to operate inside the window as much as across it.

### 1.5 Two things I found that are sharper than the bead's own argument [V]

**(a) The cap is co-located with the typical batch size, and `newEvents` are sliced first.**
`causal-pass.ts:157-160`:

```
const newEvents = newEventRows.slice(0, cap).map(toScopeEvent);
const remaining = Math.max(0, cap - newEvents.length);
const neighbourhoodEvents = neighbourhoodAll.slice(0, remaining).map(toScopeEvent);
```

When a promotion mints 200 or more events, `remaining === 0` and `neighbourhoodEvents` is **empty** —
the only cross-batch bridge is closed completely for that epoch. Measured batch sizes: **median 194,
mean 192, max 299**; **39 of 93 batches exceed 200**, containing **9,043 of 17,847 events (50.7%)**.
**[I]** So for roughly half the substrate the neighbourhood bridge had zero or near-zero slots. The cap
is not a generous ceiling that was occasionally brushed; it sits on top of the modal batch.

**(b) `neighbourhoodEdges` are passed unsliced while their endpoint events are dropped.**
`causal-pass.ts:172` sends `[...neighbourhoodEdgesById.values()]` in full, with no cap and no filter
against the surviving event set. Combined with (a), the agent is handed a list of edges referencing
events it was never shown, and `causal_agent.py:126-131` renders them as bare
`causeEventId -> effectEventId` lines under "Existing causal edges (do not duplicate)". That is a
prompt-coherence bug independent of the scoping question. Fix size: **one-line** (filter by the kept
event ids, or cap them).

Sub-fix sizes: (a) is **one-line** if the answer is "reserve a neighbourhood budget" (e.g. slice
`newEvents` to `cap * 0.7`); (b) is **one-line**. The bead's actual question — options (a) periodic
global sweep, (b) causal-candidate-following scope, (c) accept and document — remains
**needs-design**, and I would add option (d): keep the window but **raise or remove the cap**, since the
measurements show the cap alone closes the bridge on half the corpus.

**Verdict: STALE-PREMISE.** Not merely "0 rows today" — the premise is **unreachable on this substrate**,

### 5.1 There is nothing to embed, and re-running detection would not change that [V]

- So I approximated `detectCausalPatterns` in SQL on the *current* graph. Its template node is
  `(entities.entity_type, coalesce(fact_predicates.category, causal_events.predicate, ''))`
  (`causal-patterns.ts:300-331`), clustered by hash, and a cluster becomes a pattern only at
  `instanceThreshold = 3` (`causal-patterns.ts:114-119`). Result over all **142** two-hop chains:

  `concept|scales_faster_than >> concept|stabilizes_with >> concept|suppresses` — n=1 each.

### 5.2 Root cause [V]

`causal_events` carries **6,652 distinct predicates**. `fact_predicates` — the category catalogue the
normaliser joins to — has **48 rows**. Only **162 of 17,847 events (0.9%)** resolve a
`predicate_category`. For the other 99.1% the documented "Q2 fallback" at `causal-patterns.ts:329`
substitutes the **literal predicate string**, which on a free-form arXiv extraction is near-unique.
Template collision is therefore impossible at any plausible threshold, and no amount of re-running
detection produces a pattern. **[I]** Pattern detection on this substrate needs a predicate ontology
fold, which is the thing CLAUDE.md records as tested and **FAILED** (docs 40/41, 3.7%) — so this is not
a small upstream unblock either.

### 5.3 The chain-pruning half is independently unreachable [V]

PathRAG-style pruning between an anchored cause/effect pair needs alternative paths to rank. The graph
has **12** three-hop and **3** four-hop paths in total, and its largest connected component is **7 event
nodes**. There is no path set to prune.

- `src/index.ts:1078 (invokeReasoningAgent)` — `invokeReasoningAgent` is now at `index.ts:1427-1430`

## 6. Is there any global causal re-sweep? No. [V]

Both `nmemo-umf` and `nmemo-an9` hinge on this and both are right about it.

- **Only one caller mints causal edges.** `runCausalPass` is imported at `pipeline.ts:17` and called at
  `pipeline.ts:1104`, inside the per-epoch flow. The only other references are its own definition
  (`causal-pass.ts:104`) and a comment.
- **No endpoint.** The causal-adjacent HTTP surface in `index.ts` (read with `grep -a`, per the NUL-byte
  trap) is: `/api/patterns/detect` (1176), `/api/patterns/promote` (1196), `/api/patterns` (1208),
  `/api/patterns/:id/instances` (1225), `/api/causal-edges/:id/history` (1265), `/api/reason` (1417),
  `/api/reason/query` (1494), `/api/garden` (880), `/api/reasoning-reports*`. None of them runs a causal
  pass or mints a causal edge.
- **No job.** `startScheduler` (`scheduler.ts:388-408`) registers exactly three: `drift-patrol`,
  `reasoning-patrol`, `source-refs-drift-patrol`.
- **No CLI.** `platform/scripts/` contains benchmarks, snapshot tooling, `backfill-predicate-embeddings.ts`,
  and three `verify-*-live.ts` scripts. `verify-causal-live.ts` seeds one two-event scenario and calls
  `runCausalPass` once against it (its own header says so) — a verification harness, not a sweep. A
  repo-wide grep for `re-sweep|resweep|globalCausal|causalSweep` hits only a test file.
- **The one recurring causal-adjacent job cannot mint.** `reasoning-patrol` calls `POST /api/reason`
  with the `reasoning_agent` actor. It holds `expire_causal_edge`, `revise_causal_edge`,
  `create_contradiction` and the reads, but `create_causal_edge` no longer exists and
  `propose_causal_edge` throws without `MNEMO_EPOCH_ID`, which `invokeReasoningAgent` never sets (§2.1).
  So the global patrol can retire and revise causal structure but can never add any.

**[I]** Net: the causal graph is append-only through exactly one delta-scoped seam, and the only global
pass that visits it is structurally incapable of adding an edge. Whether or not delta-scoping caused
doc 44's thinness, the *absence of any re-sweep* means nothing will ever revisit a decision the window
got wrong — and that part needs no causal inference to establish.

## Method notes and limits

- All SQL ran against `cognitive_test` via `docker exec -i nmemo-postgres-1 psql -U cognitive -d cognitive_test`,
  SELECT-only apart from two **TEMP** tables plus a `DO` block used to compute connected components inside
  one session; nothing in a permanent schema was written.
- `causal_events` has no `epoch_id`, so every "batch" claim rests on the `date_trunc('second', created_at)`
  proxy, which I validated against `staging_causal_edges.epoch_id` (§1.3). It is good but not exact: a
  second-cluster can in principle contain two concurrent epochs, which would inflate my batch-size
  figures and hence the §1.5(a) cap argument. The 39/93 over-cap figure should be read as an estimate.
- I did not run the causal pass, the reasoning patrol, or pattern detection. The §5.1 "detection would
  find nothing" result is a SQL re-implementation of `normaliseChainsBatch` plus the cluster threshold,
  not an execution of `detectCausalPatterns`; it ignores `lookbackDays=30` (which would only *reduce*
  the chain set further) and `maxChainLength=6` (only 15 chains exceed two hops at all).
- Apache AGE was not consulted: it is retired from the read path and its `causal_graph` is dead.
